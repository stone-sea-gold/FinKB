### 坑-39 页脚数字不是物理页码

**现象**：000625 半年报 252 张逻辑表里只有 24% 的数值能在它声称的页上查到，把窗口整体
右移一页后变成 100%——**每张表都早一页**。

**成因**：`content_list_to_pages` 过去无条件用 `page_number` 块的文本当页码。第 1 页是封面、
正文页码从 1 开始（PDF 第 2 页才是「第 1 页」）时，照抄页脚就让整份文档的页码小 1。
比亚迪、赛力斯没有封面，所以一直是对的——**这个 bug 藏了三份文档才露头**。

**现在的规矩**：整份解析页码就是 `page_idx + 1`；只有按页范围解析（`--pages`，`page_idx`
从 0 重编号）才用 `page_number` 还原，由 `use_page_number_map` 显式打开。另加
`detect_page_offset()` 兜底：抽样表格数字试 −3..+3 页，命中率够 80% 才认。

**教训**：页码错不会让任何校验失败——它只会让 L0 凭证指到隔壁那一页，且看起来完全正常。
只有「把数字回查 PDF 原文」这种外部证据能发现它。

### 坑-40 宽表逐页丢空列，跨页缝合被列数判据挡住

**现象**：601127 半年报第 57–61 页是**一张**股东权益变动表，被 MinerU 切成 5 块。缝合判据
连着 4 次报「列数不一致（16 列 / 15 列）」，最后一张都没缝上。

**成因**：MinerU **按页**渲染表格，某页整列全空时会把那一列整个丢掉，于是 P57/P59 是 16 列、
P58/P60 是 15 列。列数不等是渲染副作用，不是「这是另一张表」。

**为什么没有放宽判据**：列数不一致的确有两种情形——`P65→P66` 的 7 vs 2 是两张表（正确拒绝），
这里的 16 vs 15 是同一张表。**相差 1 列无法与「恰好少一列的另一张表」区分**，而且丢的是哪一列
无法判定（P58 的值要对齐到第 5、12、14 列才能对上，中间缺的那列不知道是谁）。硬对齐等于猜测，
会把数字安到错误的列名上——这比不缝合更糟。

**现状**：照常拒绝并打印告警（`请人工核对`），表格数据一条不丢，只是 4 个分片没有列名。

**可行的下一步**（未实施）：用「明细之和 = 合计」判断缺失列的位置，或对这类分期权益表按
「表内 labeled 列名」做跨页对齐。两条都依赖具体表形，先记为已知限制。

### 坑-41 MinerU 会 OCR 错一位，且与同表的合计行矛盾

**现象**：601127 半年报 P93 坏账计提表，「新能源补贴款」行期末账面价值 MinerU 给
`52,476,375.00`，PDF 原文是 `52,476,376.00`；**同一张表的「合计」行 MinerU 又写对了**
`52,476,376.00`。`verify-cells` 因此报了唯一一个查不到的数字。

**含义**：这不是我们解析错，是上游 OCR 错一位。可贵的是**它自相矛盾**——明细与合计对不上，
所以这类错误可以用「明细之和 = 合计」自动发现，不必依赖 PDF 回查。

**教训**：`verify-cells` 查不到的 1/1647 说明外部回查有效；而「表内自洽性」是零成本的第二道网。

### ADR-025 补充（2026-10-28）：自动分批在真实文档上验证

`000625_2025_年报` 222 页 > 200 页上限，`--auto-split` 自动切 `1-200` / `201-222`，合并后
页码 1..222 连续；**跨页缝合恰好落在批次边界 `P200→P201` 上并成功**——这一条同时验证了
`merge_batches` 的偏移、`page_end` 回填与缝合判据三者在一个坐标系里。

数值回查 1856 个数字 100% 命中、偏移自检 0 页最佳、守恒律 14/14。

### 拒绝方案：「明细之和 = 合计」做自动校验

**动机**：坑-41 里 MinerU 把一位数认错，但同一张表的「合计」行是对的——这种**表内自相矛盾**
本该零成本抓出来。

**试了什么**：对每张逻辑表，取「合计/小计/总计」行之前、自上一个合计行之后的所有行当明细，
逐列求和比对，容差 0.5。

**结果**：`601127 半年报` **267 组可比，32 组不一致**，逐组看下去绝大多数是假阳性：
- 「合计」行在表里出现在**多个嵌套层级**（`流动资产合计` 上面还有分组小计），「上一合计行之后」
  这个切法不建模层级
- 并列期间的表（本期/上期）里，一组合计行跨两期
- 公允价值变动、比率这类列本来就不满足加总关系

**结论：放弃**。要修好得先建行层级模型，那比它要抓的错误昂贵得多。真值校验仍以
`verify-cells`（回查 PDF 原文，六份文档 99–100%）为准——它已经在真实文档上抓到了坑-41。

**教训**：审计判据同样适用「结构事实优先」。`verify-cells` 靠的是「这个数字必须出现在 PDF
这一页」，是外部证据；「明细之和 = 合计」靠的是对表结构的假设，假设一错就满屏报警。

### 坑-42 表头探测窗口是从单份文档数出来的数

**现象**：601127 年报 P131「项目|期末余额|期初余额」这张表没认出表头，整行掉进数据行。
同页另一张一模一样的表却认对了。

**成因**：判据③原本只看「后面的 `HEADER_LOOKAHEAD_ROWS = 3` 行内有没有数值」。这张表前三行是
`定期存款`、`委托贷款`、`债券投资`，**值全空**，数值到第四行才出现——3 行窗口刚好差一行。

**修法**：删掉 `HEADER_LOOKAHEAD_ROWS` 常量，改成「后面任意一行有数值」。判据仍是结构事实
（本行无纯数值 + 至少两个非空 + 后面有数值），只是不再有窗口这个凭空的数。

**代价评估**：八份文档全量对比——逻辑表 2289 → 2286，有表头 **2027 → 2083（+56）**，
裸表 **183 → 152（−31）**，有表头率 88.6% → **91.1%**；所有文档的数值总数与总和**逐位相同**
（表头行本就不含纯数值，抬升只是换了个字段）。257 项测试全过。

**教训**：判据里凡是「看前后 N 行/±N 页」的数，都是把某一份文档的排版当成了普遍规律。
能用「全表任意行」就别用窗口。

### 坑-43 派生产物会和代码漂移，而且看不出来

**现象**：改完 kv 判据、caption 判据、表头判据之后，`audit` 的各项指标都没变，看起来一切正常。
实际上 `data/parsed/*/logical_tables/*.md`、`tables/*.md`、`page_anchored.md` 还是旧代码生成的。
18 份重跑一遍才发现：`000625_2025_年报` 有 **180 个文件**变了、`601127_2025_年报` 34 个、
`601127_2026_半年报` 31 个。变化比如 `kind=data → kv`、`caption=（除特别注明外，金额单位均为
人民币元）` 变成 `section=流动负债:`。

**为什么看不出来**：`audit._analyze()` 是**从 `content_list.json` 现算**的，从不读磁盘上的
`.md`。所以「重算指标不变」只证明代码对同一份输入的判断没变，**完全不能证明产物是新的**。

**修法**：`src/finkb/version.py` 的 `pipeline_fingerprint()` 取六个参与解析的源文件内容哈希，
`cli` 写进 `report.json`；`audit invariants` 新增「解析版本」一条，缺戳或不一致就报失败。
用内容哈希而不是手写版本号，是因为**没人会记得 bump**。

**教训**：只要有一份产物是「生成物 + 缓存」，就必须给它一把尺子证明它是新的。指标口径再严，
量错了对象也没用。

### 坑-44 R2 要求「下层每列都落在分组区间」，漏掉「一列就是一组」的列

**现象**：`股份性质 / 本次变动前(2列) / 本次变动(1列) / 本次变动后(2列)` 这种表，第二层
`数量(股) / 比例 / 送红股及资本公积金转增股本(股) / 数量(股) / 比例` 没被认成表头层，
压平后 `本次变动前` 重复出现在两列上，而「送红股…」那一列干脆没有名字。

**根因**：R2 要求下层的每个自有单元格都落在上层 `colspan>1` 的分组区间内。可 MinerU 对
**「一列就是一组」的列不写 colspan**（`本次变动` 就是），于是 `本次变动` 那列永远「不在
任何分组内」，整层被否。

**修法**：R2 增加「**整列一格**」豁免——上层某个单元格 `colspan == 1` 且有名字时，下层对
这一列改名是合法的细分，不算越界。判据仍是 HTML 结构事实，没有引入新阈值。

**实测**（18 份）：多层表头 **496 → 502**；非空重名列的表 **35 → 28**；有表头率 91.1% → **91.7%**；
裸表 163 不变；18 份守恒律全过；265 项测试。新增的 6 张人工核对全部是真双层表头
（如 `601127 年报 P25_T29` 的 `销量(辆)/产量(辆)` 分组、`002594 半年报 P20_T07` 的
`本报告期/上年同期` 分组）。

**失效条件**：上层有 `colspan>1` 分组、且**第一行数据全是短文本**（无任何纯数值）时，可能
把数据行当成第二层表头。实测 18 份未出现；真出现时新表头会把数据行吃掉一行，从数值个数
的变化能立刻看出来。

### 坑-45 表头单元格的列区间从 0 起数，`rowspan` 进位后就整体左移

**现象**：`000625_2025_年报#P88_T85`（股东权益变动表，15 列）压平后出现
`项目/归属于母公司所有者权益/股本` —— 第 0 列本该只是「项目」，却把上层分组名和下层列名都串了进去，
而真正的分组名 `本期金额` 整层丢失。列名整体右移一格，看着像对的，比没有列名更危险。

**根因**：`_header_cell()` 用 `_cell_columns()` 算「本层每个单元格覆盖哪几列」，而
`_cell_columns()` 是**从第 0 列开始数**的。可这一行的第 0 列被上一层 `rowspan` 的「项目」占着，
本行自有单元格实际从第 1 列开始 —— 于是每个格子的区间都少了这一格。

**修法**：新增 `_cell_columns_at(raw_rows, target)`，走一遍与 `_expand_merged_cells()` **完全相同**
的列游标（遇到 rowspan 进位先跳列），三者从此不会失步。`_header_cell()` 与 `_count_header_layers()`
都改用它。

**同一处还牵出坑-46**：表头层数上限写死 `limit = 2`（最多 3 层）。这张表是**四层**——
`本期金额 / 归属于母公司所有者权益 / 股本·其他权益工具·… / 优先股·永续债·其他`，
第 4 层被当成数据行，于是数据里凭空多出一行 `| 项目 | 股本 | 优先股 | … |`。
上限删掉，改由 R1/R2/R3 三条结构判据自然终止（行数耗尽即停）。

**实测（18 份）**：非空重名列的表 **28 → 19**；逻辑表 2705、有表头 2481、裸表 163 **全不变**；
**数值个数 42260 逐个不变**（被收进表头的 7 行全是纯文字层）；18 份守恒律全过；265 项测试。

### 坑-47 只有「精确率」没有「召回率」，表格整张丢了也看不出来

`verify-cells` 抽样核对的是「我们表里的数字在 PDF 原文里查得到吗」——这是精确率。
如果 MinerU 把整张表丢了，我们的表里没有它的数字，精确率依然是 100%。

补 `tools/audit.py recall`：把 PDF 每页的数字（去千分位、去空白后做**子串**比对）拿去
解析结果里找。子串比对而不是正则匹配，是因为 PDF 抽取有两种失真：把数字拆到两行
（`1,007,771,544.1` + `3`）、把两个数字粘成一串（页脚 `86` + `9,638,215.61` = `869638215.61`）。

**实测 18 份**：19782 个数字，页内对上 98%，加上「他页找到」共 19577 个；剩 205 个逐一看
上下文，**全是 PDF 文本层粘连**（页脚、图表刻度、公告编号与年份）。**召回实为 100%**。


### 坑-48 跨页重复打印的表头被当成数据行

MinerU 对跨页的宽表常常把两页并进**同一个**表格块，下一页又打了一遍表头；那一行于是
成了「数据行」。表面上只是多一行，实际有两个后果：这一段的列名中间出现空洞（`''`），
而且换了段落以后同一份表头会被再吞一次。

判据是**同名**：这一行与列名在多列上一个字不差——真正的数据行不会这样。
表级走 R4（`markdown_blocks._count_header_layers`），段级走
`section_splitter._absorb_repeated_header`；吸收时顺带把「上层留空、这一层才有名字」
的格子补进列名。

**实测 18 份**：表头空洞 39 → 21 张，数据行 −41（全是重复表头），
逻辑表 / 有表头 / 裸表 / 多层表头 / 数值 42260 个**全不变**。

### 坑-49 一次读超时就让整份文档作废

309 页的长城汽车年报走 `--auto-split`，两批都提交成功，轮到轮询/下载时 `requests`
抛了 `ReadTimeout`（`read timeout=60.0`），**整份文档直接作废**——前面那十几分钟和
309 页额度全白费。批处理跑十几分钟，中间撞一次网络抖动是常态，不是异常。

`MineruClient._send()`：读超时 / 连不上 / 断连 / 5xx 一律退避重试三次，
4xx（比如配额用尽、签名错）直接报错不重试——重试也没有意义。
`RETRY_ATTEMPTS` / `RETRY_BACKOFF_SECONDS` 是运维参数，不是解析判据。

### 坑-50 两个数字粘成一格，读出来是错的

长城汽车 P19 的产销表里有两格是 `602,855430,242` 与 `600,008389,045`——本该是
`602,855` 和 `430,242` 两个格子。MinerU 少输出了一个 `<td>`，我们又按「一格一个数」
去读，于是**两列的数被拼成了一个不存在的数**。`verify-cells` 正是因为查不到这个数才
把它暴露出来（它是唯一一处「数字在 PDF 里找不到」的真缺陷）。

`tools/audit.py numbers`：千分位必须「首组 1–3 位、其余每组恰好 3 位」。粘连
（`602,855430,242`）和小数逗号（`0,01%`）都不满足。**只报不改**——把 `602,855430,242`
拆成两格需要知道列边界，猜错了比不拆更糟。全语料 19 份共 **6 处**。

### 坑-51 资产负债表差 2 元，是报表自己的事

广汽的**母公司**资产负债表：资产 `214,943,407,093`，负债 `105,259,714,163` + 权益
`109,683,692,932` = `214,943,407,095`，差 2 元；而**上年同期那一列分毫不差**。
三个数在 PDF 原文里都查得到（第 100/101 页），所以不是解析错，是报表自己四舍五入。

原先的判据是 `abs(delta) < 1`，直接把整份文档判失败。改成**只按相对量级**给容差
（一百亿分之一）：2000 亿的报表允许差 21 元，一亿的报表只允许差 0.01 元。
代价说清楚——大公司里 1 元的读错确实看不出来，这是算术本身的分辨率极限。

### 坑-52 银行的现金流量表，流出是负数

招商银行半年报：`流入 730,917 − 流出 (596,456) = 1,327,373`，而表列净额 `134,461`。
不是解析错——银行/保险把流出印成**带括号的负数**，制造业印成正数。
判据从 `inflow - outflow` 改成 `inflow - abs(outflow)`，两种写法都对；
制造业那些文档的输出逐字未变（绝对值不改正数）。

同类差异还有：银行的「利息净收入」「拨备覆盖率」等指标在制造业文档里根本不存在，
所以这类检查只能覆盖三家都有的报表结构，指标类不做守恒。

### 坑-53 连着两行「标签 + 跨列的值」，被当成了双层表头

长安 T51 的 HTML 是
```
<tr><td>内部控制评价报告全文披露日期</td><td colspan="2">2026年4月11日</td></tr>
<tr><td>内部控制评价报告全文披露索引</td><td colspan="2">巨潮资讯网(...)</td></tr>
```
第 0 行 2 个非空格、本行无纯数值、后面有 `100%` —— 三条纯数值推断全中，于是判成表头；
第二行又被当成第二层，压平成 `['披露日期/披露索引', '2026年4月11日/巨潮资讯网', ...]`，
整张表按列读，把后面的 `类别|财务报告|非财务报告` 那张 3 列表也压成同一张。

判据：**连着两行都是「2 个自有格、第 2 个跨满剩余宽度」⇒ 这是键值对，不是表头**。
只认单行会把 126 张真·双层表头（`项目 | 本期金额(colspan=3)`）一起干掉；
认两行只动 3 张，且 3 张都是真错（长安 T51、比亚迪 T75、长城 T131 的可转债/内控自评表）。

全语料：逻辑表 3834 不变、有表头 3510 → 3507（去掉 3 个假表头，其中 2 张的后续段落
拿到了真表头）、守恒律 21 份全过。

### 拒绝方案：用「跨表一致性」当稳定性指标

想法很自然：同一张表在年报和中报里都披露过，两次解析结果应当一致，不一致就是不稳定。
试了三种配对，**全部不成立**：

1. **跨文档、按列下标比**：年报是「年末/上年末」，中报是「6 月末/年初」，同一列不是同一个时点
   —— 不一致率 71%~82%，全是内容差异
2. **跨文档、按列名比**：`期末余额` 在两份文档里指的不是同一天，同列名照样不可比 —— 54%~80%
3. **同文档、按行名比**：剩下的大多是**同一张宽表被切成两段**（`P184_T131#S01` vs
   `P185_T132#S01` 行名重合 93%），或两期并排的同名表 —— 不一致率 30%~99%

结论：**这个语料里「看起来重复的表」全是不同期间或不同分段，没有一对是真正的同内容重复**。
稳定性只能靠外部证据（`verify-cells` 回查 PDF 原文）和内部算术（守恒律），不能靠比对。
记在这里，免得下次再花一轮重试。

### 坑-54 「后面有数值」这个判据，把「6、7、9、13」挡在门外

税种表 `税种 | 计税依据 | 税率` 的数据行是 `增值税 | ... | 6、7、9、13`，
折旧表是 `土地使用权 | 33-50 年 | 年限平均法` —— **整表没有一个「纯数值」**，
于是纯数值推断的第 ③ 条（后面有纯数值）永远不成立，表头识别不出来。

判据从「后面任意一格是纯数值」放宽成「后面任意一格**含数字**」。
一次试错记录：我同时加了「首行不含数字」的条件，结果有表头数从 3707 掉到 3004 ——
财报表头里成片是 `2025年 / 2024年`，这条把最常见的一类全杀了，立刻撤回。

另一个副作用也要堵：两列表 `统一社会信用代码 | 9150000020286320X6` 现在会被当表头，
所以补一条——**两列表里第二格超过 12 字就是值不是列名**（真列名是「重要性标准」「金额」这种短的）。

全语料：有表头 3707 → 3815（**94.5%**），逻辑表 4039，守恒律 22 份全过，`verify-cells` 100%。

### 坑-55 核查工具少算了一种去向，把「0 行丢失」误报成 44 行

做「一行的去向」核查时，我列了四种合法去向：进逻辑表、成了段内表头、
成了分节标题、被当重复表头吸收。跑出来 44 行对不上，我据此写了「季报股东信息
的多行表头被吞」这个结论。

**结论是错的。** 漏掉的第五种去向是「成了**该段**的表头」——多行表头会被
`html_table_layout` 剥离，剥离后的行**不落在任何 `row_range` 里**，因为它们
在 `row_range[0]` 之前。加上这一段（上一段结束到本段起始之间的行）之后：

```
全语料 22 份、4039 张逻辑表 —— 没有去处的行：0
```

教训有两条：

1. **核查工具的漏洞和被测代码的漏洞长得一样**，都会表现为「有几行对不上」。
   写核查器时要先把「合法去向」穷举干净，穷举不干净就会把自己算不进去的那一类
   报成缺陷。
2. 报数字之前先问一句「这个数如果是真的，它应该长什么样」。44 行全落在
   12 份季报的同一种表上，这个分布本身就该提示「可能是同一类版面特性」。

现在这条已经升格成守恒律第 16 条「行去向」，任何一次改动只要吃掉了行就会红。

### 坑-56 一行四格「键、值、键、值」被当成了四列表头

`股票简称 | 长安汽车、长安B | 股票代码 | 000625、200625` 是**一行**四格，
键和值交替排列。表头判据看到「四格、全是中文短串、后面有数字」，就认成了表头，
结果这张表的列名变成「股票简称/长安汽车、长安B/股票代码/000625、200625」，
真正的数据从第二行才开始。

判据：**偶数格、键不带数字、值里带数字、且没有任何一格是年份**，四个条件同时成立
才是键值行。四个条件的来历都是被真实数据打回来的：

| 条件 | 不加会怎样 |
|---|---|
| 值里带数字 | `接待时间/接待地点/接待方式/接待对象类型` 这种真表头被误杀 |
| 键不带数字 | `中国 / 130,796,138,817 / 79.75% / 127,306,652,835` 这种**数据行**被误杀 |
| 没有年份格 | `项目 / 2025年 / 2024年 / 同比` 这种期间表头被误杀 |
| 偶数格 | 三列表头本来就该是表头 |

全语料：有表头 3815 → 3804（**去掉的 11 张都是真键值行**，逐张核过），
逻辑表仍 4039，守恒律 22 份全过，`verify-cells` 100%。

同时把 5 张**真实表格 HTML** 抠进 `tests/fixtures/tables/`，配 `tests/test_real_tables.py`
做回归——合成用例只能覆盖「我想到的形态」，这些覆盖的是 MinerU 的真实输出
（没有 `<th>`、没有 colspan 标记）。

### 坑-57 MinerU 补出的整列空格子被当成真列

`股东名称 | '' | 持有无限售条件股份数量 | '' | 股份种类 | 数量 | ''` —— 一张四列的表
在 MinerU 输出里是七列，多出来的第 2、4、7 列**永远是空串**（跨行合并与版面留白补的）。
问题有两个：按列名取值时每个空列都要多判一次；同一张表的不同分片会因为各自丢了
不同空列而列数不一。

修法：缝合**之后**删掉「表头没名字、数据也全空」的列。全语料含空列的表 **50 → 34**、
空列总数 **213 → 99**（其余是这个分段没用到、但整表有数据的列，必须留）。

**不能在缝合前删**：删列会改变分片宽度，让本来就该拒的 16/15 变成别的数字，
属于用副作用换副作用。第一版就是在 `html_table_layout` 里删的，`test_two_kv_rows_are_not_a_header`
与 `test_stitched_rows_have_uniform_width` 同时红——两个测试正好各自扑到一边。

### ADR-028 语料基线：让「这一版比上一版好」变成可判定的事

**背景**：每改一版都能报出「有表头 94.2%」，但没有人记得上一版是多少。二十几轮下来，
`corpus` 输出的数字是**状态**不是**变化**——改坏了也能看到一张漂亮的表。

**决定**：`tools/audit.py baseline` 把 22 份文档的 `pages / logical / header /
invariants` 写进 `config/corpus-baseline.json`（进 git，约 3KB）；`corpus --baseline`
对照它，**只在变差时报错**：

- 某份有表头张数减少 → 报「10 → 8（退步 2 张）」
- 某份守恒律通过数减少 → 报出来
- 某份文档从语料里消失 → 报出来（路径写错、产物被误删都会这样）

表头变多、新增文档、表数因判据改进而变**都不报**——那是改进，不是退步。

**为什么只存这五个数**：基线要进 git、要被 review。明细（每张表的表号）在
`data/reports/` 里，基线只回答「有没有变差」。

**失效条件**：基线是**在同一份 `content_list.json` 上**算出来的。换了 MinerU 版本、
重新解析出新的 `content_list.json`，基线就该重写（`audit baseline` 直接覆盖）。

`scripts/check.sh` 已接上，退步时整条命令退出码 4。

**补充（2026-10-28 晚）**：基线里加进**数值回查**两个数字（`verify_checked` / `verify_missing`），
`corpus --pdf-root ../raw` 会为每份文档抽样把数字回查 PDF 原文。

这是整条验收链上**唯一对着 PDF 原文**的检查——单元测试、守恒律、快照 diff 全都建立在
「我们自己解析出来的数」上。全语料 **24746 个抽样数字，4 个查不到（99.98%）**，四个全是
MinerU 把两格粘成一格的 OCR 错位（`601127_2025_半年报` 1 个、`601127_2025_年报` 1 个、
`601633_2025_年报` 2 个），已在基线里固定下来，**以后多出一个就说明代码改坏了**。

代价：读 22 份 PDF 约 40 秒（本地，不耗 MinerU 额度），已进 `scripts/check.sh`。



### 坑-58 「资产总计」不止一个，按行名取第一条会拿到勾稽表

**症状**：万科 A 2025 年报资产负债表恒等式差 `-1,020,520,769,249.71`，报「资产
102,062,283.15 vs 负债 784,762,773,496.17 + 权益 235,860,058,036.69」。

**根因**：文档里叫「资产总计」的行有两处——一处是**资产构成表**（万元口径，
`102,062,283.15`，同一行还带 `100.00` 的占比），一处是真资产负债表
（`1,020,622,831,532.86`）。`_locate_row` 按文档顺序取第一条，恰好取到勾稽表。

**修复**：把「资产总计 × 负债合计 × 权益合计」的所有候选**按三元组枚举**，用恒等式
自己挑：先筛「等式在容差内成立」的组合，其中取**资产最大**的一组（合并报表的资产总计
一定 ≥ 母公司报表）；等式都不成立才退回残差最小的一组，把差额照实报出来。

同时把取值方式从「`_first_numeric_column` 定一列」改成「**该行最左边的金额格**」——
万科真报表那一行是 `['资产总计', '', '1,020,622,831,532.86']`，定列取法会取到中间那个
空串从而漏掉整张表。避开的是「附注」列里的 `62`、`61`（与坑-38 同源）。

**测试**：既有 4 个资产负债表用例全绿；24 份语料 16 条守恒律全过，其中万科从 1 条失败
变 16 条全过，比亚迪输出逐字未变。

### 坑-59 破折号不是「取不到数」

**症状**：中国神华 2025 年报现金流量表恒等式报「行存在但取不到数值」，`P166_T145#S01`
的筹资活动流入小计整行是 `['筹资活动现金流入小计', '', '-', '22,480']`。

**根因**：`_amount_in_column` 只把**空单元格**记 0，`-` 交给 `_parse_number` 返回 `None`。
可报表里 `-` / `—` / `/` 恰恰就是「本期无金额」，与空单元格同义。

**修复**：加 `_ZERO_MARKERS = {"-", "--", "—", "——", "/", "－"}`，命中即记 0。
结果 `0 − 95,019 = -95,019`，与表列净额一致。

**为什么不是放宽**：真丢数据时这一格会是**缺行**或**乱码**，不会被记成 0，等式仍然对不上。

## 3. 架构与数据流

### 3.1 四层结构（方案层）

```
L3 交互层   三栏工作台 / 路由徽标 / 三视图
L2 知识层   Markdown Wiki + FTS5 + 链接图 + _draft 隔离 + lint
L1 事实层   DuckDB（数字只由 SQL 计算）
L0 凭证层   PDF + 物理页码锚 + 跨页缝合 + 向量兜底
```

**当前代码只实现了 L0。**

### 3.2 L0 内部数据流（实现层，含格式边界）

```
PDF
 │
 ├─[生产路径] MinerU 在线 API
 │     content_list.json  ──┐
 │                          │
 └─[兜底路径] pypdf 逐页    │
                  │         │
                  ▼         ▼
        ┌──────────────────────────────┐
        │  content_list_to_pages()      │  ← 唯一的 MinerU 格式适配层
        │  OfflinePdfParser.parse()     │  ← 唯一的 pypdf 格式适配层
        └──────────────┬───────────────┘
                       ▼
        ┌──────────────────────────────┐
        │  Page / Block / TableBlock    │  ← 本项目 IR（层内唯一真相）
        └──────────────┬───────────────┘
                       │
                       ├─ strip_running_noise()   打标噪音块、删噪音行
                       ▼
                   stitch_tables()               按「内容块」缝合
                       ▼
                   StitchedTable                 交给 L1
```

**关键约定**：`noise_filter` 与 `table_stitcher` **完全不知道数据来自哪个解析器**，
它们只操作 IR。这是有意的解耦（见 ADR-008）。

### 3.3 落盘格式

页码锚定 Markdown —— L0 的持久化形态，也是人工核对与调试的入口：

```markdown
<!-- META: {"doc":"002594_2025_年报","page":42,"section":"第三节 管理层讨论与分析"} -->
| 项目 | 2025年 | 2024年 |
| --- | --- | --- |
| 营业收入 | 77,201,000 | 60,231,500 |
```

一条 META 开启一个块，块内容持续到下一个 META。

## 5. 关键设计决策（ADR）

每条含：**决策 / 理由 / 影响 / 失效条件**。「失效条件」很重要——不要把决策当教条。

### ADR-001 按数据类型分层，而不是按模块分层

- **决策**：L0 凭证 / L1 事实 / L2 知识 / L3 交互。数字归 L1，定性叙述归 L2。
- **理由**：v1 计划把「数值」和「定性知识」混在同一层，让 LLM 生成 Markdown 表格
  再事后校验数字。但 LLM 不擅长算术，校验是补救而非解决。
- **影响**：v1 的 Write-Gate「数字存在性校验」被整体取消。
- **失效条件**：若某天必须让 LLM 直接产出数值（例如纯叙述型报告），分层要调整。

### ADR-002 检索以 FTS5 为主，向量为辅

- **决策**：L2 主检索用 SQLite FTS5 + BM25 + jieba；向量只服务定性长尾。
- **理由**：用户抱怨「检索概率性不可解释」。BM25 命中是**词**，可以展示给用户；
  向量命中是**数**，无法解释。且会计科目/股票代码这类精确匹配 BM25 天然更强。
- **影响**：v1 的 Qdrant 双路向量 + rank-bm25 稀疏向量方案被废弃。
- **失效条件**：语料扩到单主题下 10 万+ 文档、大量同义改写查询时，需要重新权衡。

### ADR-003 不做 GraphRAG，用「链接图 + 关系边表」

- **决策**：Markdown 显式双向链接当图用；需要多跳时查 L1 的 `relations` 表。
- **理由**：语料只有 3 家公司（2026-10-21 决策时；现为 10 家），实体图谱投入产出比极差；GraphRAG 索引成本高。
- **失效条件**：文档量到千级、需要跨文档实体消歧时再考虑。

### ADR-004 L1 采用两段式抽取（补丁 P1）

- **决策**：
  1. **LLM** 只做语义对齐与原值摘录（`raw_text_matched` / `value_raw` / `unit_raw`），
     **严禁换算与四舍五入**；
  2. **Python** 反查原文命中后确定性归一化入库。
- **理由**：A 股年报表格行列名高度非标（「汽车及相关产品」/「新能源汽车」/「汽车整车」
  都可能指同一指标），纯正则无法映射；但让 LLM 做数字运算会引入幻觉。
- **影响**：反查采用三级匹配 `exact` → `normalized` → `numeric`，全失败进
  `unmatched_pool`，**禁止静默丢弃**。`exact` 匹配率是解析质量指标（验收 ≥80%）。
- **失效条件**：若表格格式高度规整（如监管模板统一），可退化为纯代码解析。

### ADR-005 预建宽表视图 + 枚举注入（补丁 P2）

- **决策**：`facts` 是 EAV 纵表，但给 Text-to-SQL 提供 `v_company_annual_wide` 宽表；
  System Prompt 强制附带完整 `metric_dict` 枚举。
- **理由**：LLM 面对纵表写多指标跨期对比需要大量 Self-JOIN / `CASE WHEN`，易出错；
  且会臆造指标名导致空集。
- **失效条件**：指标数极大（>100）时宽表列会爆炸，需改回纵表 + 模板化 SQL。

### ADR-006 MVP 保留向量检索，用 numpy 不用 DuckDB `vss`

- **决策**：L0 兜底链路用 `bge-m3` 稠密向量 + `bge-reranker-v2-m3`，
  存储用 **numpy 暴力检索 + `.npy`**。
- **理由**：预计 3k–6k 个子块 × 1024 维 float32 ≈ 12–24MB，点积毫秒级；
  `vss` 扩展需联网 `INSTALL`，破坏离线可复现性。
- **失效条件**：语料扩到 10 万块以上，或需要元数据过滤的 ANN 时。

### ADR-007 唯一键含 `source_doc`，重述视为知识库特性（补丁 P4）

- **决策**：`UNIQUE (company, period, metric_id, caliber, source_doc)`；
  `facts_dedup` 视图按 `source_doc` 降序取最新口径；跨年报同期间数值冲突时
  自动生成 L2 的 `contradicts` 记录。
- **理由**：2025 年报内含 2024 同期数（可能重述），与原口径可能不一致，
  用旧约束会主键冲突丢信息。
- **影响**：冲突不是 bug，是 Wiki 的价值——把矛盾显式暴露供人裁决。

### ADR-008 IR 与外部解析格式解耦

- **决策**：`Page`/`Block`/`TableBlock` 是层内唯一真相；外部格式只在两个适配函数里出现。
- **理由**：MinerU 字段随版本变化（实测规范里 `middle.json` 已改名 `layout.json`）。
  把格式细节限制在一个文件里，换解析器成本最低。
- **影响**：新增解析器 = 新增一个 `xxx_to_pages()`，其余层零改动。
- **代价**：**清洗是否充分取决于 IR 的块粒度**，同一页眉在 pypdf 里是「块内的行」、
  在 MinerU 里是「独立的块」，两条路径必须分别验证（见 §7 坑-05）。

### ADR-009 噪音识别用「统计签名」，不用固定文案

- **决策**：把候选行的数字替换为 `#` 得到签名，签名在超过阈值比例的页面重复出现
  即判定为运行页眉/页脚。
- **理由**：硬编码「比亚迪股份有限公司」换一家公司就废；统计特征天然可迁移。
- **参数**：`min_pages=3`、`min_ratio=0.30`、阈值硬下限 2、
  `scan_head_lines=2`、`scan_tail_lines=2`、签名有效字符 ≥4、长度 ≤80。

### ADR-010 噪音「打标不删除」

- **决策**：删噪音**行**；若块因此变空则置 `is_noise=True` 并保留占位，
  需要物理移除时调 `drop_noise_blocks()`。
- **理由**：① 保留审计信息；② 让缝合能跳过噪音块，即使清洗不彻底也不会误判
  （见 ADR-011）。
- **影响**：`drop_noise_blocks` 后 `block_index` 与页内位置不再一致，
  因此**缝合一律用页内位置索引，不用 `block_index`**。

### ADR-011 缝合判据用「内容块」而非「块」

- **决策**：定位页首/页尾时用 `first_content_index()` / `last_content_index()`，
  跳过 `is_noise=True` 的块。
- **理由**：年报每页页首都有运行页眉。若它被解析成独立块，「第 N+1 页第一个块是表格」
  这一判据直接失效。跳过噪音块使缝合**不依赖清洗是否彻底**。
- **影响**：清洗与缝合是互补的两道防线，不是替代关系。

### ADR-012 表格表头按 `<th>` 判定，不走 Markdown 往返

- **决策**：从 MinerU 的 `table_body`（HTML）直接构造 `TableBlock`，
  首行有 `<th>` **或首行单元格全部 `rowspan≥2`** 才是表头，否则 `header=None`。
  （2026-10-21 实测修订：MinerU 用 `<td rowspan="2">` 做表头，没有 `<th>`，
  原判据在真实数据上失效，见坑-12。）
- **理由**：Markdown 管道表**语法上必须有表头**。若走「HTML → Markdown → 再解析」，
  无表头的跨页续接表会被强行套上表头，缝合时被判为「自带表头的新表」而拒绝拼接。
- **影响**：`html_table_to_markdown` 仍存在（用于落盘与人工核对），
  但**不得**用于构造 `TableBlock`。

### ADR-013 页码行识别要求数字等于物理页码

- **决策**：`is_page_number_line(line, page_number)` 只在数字**等于该页物理页码**时
  返回 True，且仅在文本块头/尾极小范围或「整块只有一个非空行」时启用。
- **理由**：页眉形如 `公司名 年份 报告全文  44`，签名只能删掉文字部分，
  页码 `44` 会作为独立行或独立块残留，进而让缝合误判「页首第一个块是文本」。
  要求数字等于页码是为了避免误删正文里的真实指标值。
- **失效条件**：若页码与物理页码不一致（如正文页码从封面起算），此规则会失效，
  需要改为「数字落在 [page-2, page+2] 容差区间」。

### ADR-014 语料锁定 2025 年，不补拉历史

- **决策**：使用工作区 `raw/` 已有数据；不补拉 2023/2024 年报。
- **理由**：用户明确要求用已有数据。
- **影响**：跨期对比只能靠 ① 2025 年报内的「上年同期」列；② 2025 vs 2026 半年报。
  **重述场景因此变成必然而非边缘**，ADR-007 从防御性设计升级为必需项。

### ADR-015 MinerU 的类型标签优先于统计推断（实测新增）

- **决策**：解析 `content_list.json` 时，`type ∈ {header, footer, page_number,
  aside_text, page_footnote}` 的块**直接标记 `is_noise=True`**；
  `noise_filter` 的统计式清洗降级为**兜底路径**（服务 pypdf）。
- **背景**：此前假设「MinerU 会把页眉页脚丢进 `discarded_blocks`、不进 `content_list`」。
  **实测发现恰恰相反**——pipeline 后端不过滤，而是输出独立块并打上类型标签
  （`type="header"`、`type="page_number"`）。VLM 后端类型更全。
- **理由**：类型标签是**确定性信号**，统计签名是**推断**。有确定信号时不应使用推断。
- **影响**：
  - MinerU 路径上 `noise_filter` 报「剥离 0 行」是**正常现象**，不代表清洗失效
  - pypdf 路径仍必须走统计清洗（没有类型标签）
  - 两条路径的清洗机制不同，测试须分别覆盖
- **失效条件**：若换成不输出类型标签的解析器（或 VLM 后端类型发生变化），
  必须退回统计清洗并重新验证。

### ADR-016 默认使用 `vlm` 后端而非 `pipeline`（2026-10-21 实测）

- **决策**：`MINERU_MODEL_VERSION` 默认取 **`vlm`**；`pipeline` 仅作为成本/兼容备选。
- **实测对比**（同一份 PDF，同样的 P43–P44，`pipeline 2.6.4` vs `vlm`）：

| 维度 | pipeline | vlm |
|---|---|---|
| P43 表列数 | 14 | 14 |
| P44 续接表列数 | **12（丢 2 列）** | **14（完整）** |
| 跨页缝合 | ❌ 拒绝（列数不符） | ✅ 成功（P43-P44，14 列 14 行） |
| 表头标记 | `<td rowspan="2">` | 纯 `<td>`，无任何标记 |
| 合并单元格 | 直接把两格并成一格（信息丢失） | 用 `colspan` 表达（可还原） |
| 数字精度 | 有 `86,3880,000.00`、`144, 778,000.00` 两处千分位错误 | 正确 |
| 横向结构 | 被压扁 | 展开成规整网格 |

- **理由**：vlm 后端把「合并」信息编码成 `colspan`（可还原），pipeline 则是**丢掉列**。
  前者可以修复，后者不可逆。
- **代价**：vlm 通常更慢、更贵（具体倍率未测）。
- **失效条件**：若额度紧张或 vlm 不可用，可退回 pipeline，但必须接受
  「复杂跨页表会丢列，缝合会失败」，且应在报告中显式标注。
- **补充（2026-10-29）**：代码里的缺省值仍是 `pipeline`（`MineruConfig.model_version`），
  实际解析由 `config/.env` 固定为 `vlm`。本 ADR 的「默认」指**本项目的运行配置**，
  不是构造函数缺省值。

### ADR-017 缝合判据：先判表头性质，再判列数；合计行即表结束（2026-10-21）

- **决策**：两处调整
  1. `_merge_verdict` **先判续接表有无独立表头，再比列数**；
  2. 起始表末行首列含「合计/总计/小计/累计」时**直接终止续接尝试**，
     且**不产生告警**（`stop_on_total_row=True`）。
- **背景**：全量 268 页跑出 6 处「疑似续接被拒」，逐个人工核对后发现
  **6 处全部是正确的拒绝**，问题出在「报告方式」而不是「判据松紧」。
- **三态判定**取代原来的二态（缝/不缝）：
  | 结论 | 含义 | 是否告警 |
  |---|---|---|
  | `merge` | 确认续接 | — |
  | `new` | 确认是另一张表（自带表头） | ❌ 不告警 |
  | `reject` | 无法确定（如无表头但列数不符） | ✅ 告警 |
- **实测影响**：告警 **6 → 1**；缝合结果不变（仍是 3 张），符合预期——
  目标是提高信噪比，不是提高缝合率。
- **失效条件**：若某类表在「合计」行之后仍有续表（例如合计后又接「其中：…」），
  会被 P1 判据漏缝。可通过 `stop_on_total_row=False` 关闭。

### ADR-018 引入两级表格模型：物理表 ≠ 逻辑表（2026-10-21）

- **决策**：`StitchedTable`（物理版面表）保持不变；新增 `LogicalTable`（逻辑数据表），
  由 `section_splitter.split_sections()` 产出。默认**不启用**切分，CLI 用
  `--split-sections` 显式开启。
- **背景**：一个 MinerU 的 `<table>` 内部可以包含多个逻辑数据表。实测 P89–P91：
  一个 11 列 85 行的物理表实为 **3 张数据表 + 2 个汇总块**。
  用户人工核实时发现了「子公司对子公司的担保情况」这处分节。
- **核心机制：表头继承**。切分**不产生无表头的子表**——没有自有表头的段继承父表
  表头（`header_source="inherited"`）。这是让 P137 现金流量表切开后仍保住
  「2025年 / 2024年」期间语义的关键。
- **实测结果**：278 物理表 → 324 逻辑表（净增 46）；
  kind 分布 data 302 / kv 8 / summary 14；262 段继承了非空表头。
- **失效条件**：若某类表的全宽行既非标题也非脚注（如纯装饰性合并），
  会被误切。可通过 `SplitOptions.narrow_heading_only` 与列数门槛收紧。

### ADR-019 表头识别增加「向前探测」与「冒号列名」两条兜底（2026-10-21）

- **决策**：纯数值分布判据外，补两条：
  1. **向前探测 3 行**是否有纯数值 —— 兜住「期间表头 + 紧邻小计行」形态；
  2. **首行非空单元格全部以冒号结尾** 且 ≥2 个 —— 兜住整表无数值的纯文本表。
  另加一条**护栏**：首行只有 1 个非空单元格时（全宽表标题）不得判为表头。
- **背景**：P137 现金流量表首行是 `['', '2025年', '2024年']`，第二行却是纯文本的
  「一、经营活动…」，只看第二行会漏判，导致**期间列语义完全丢失**。
  P118「关键审计事项」表整表无数值，任何数值判据都失效。
- **实测**：有表头的物理表从 227 → **229**；P137 现在正确识别为
  `['', '2025年', '2024年']`。
- **失效条件**：向前探测可能把稀疏数据行误判为表头；若出现此类误判，
  应收紧为「探测窗口内至少 2 行含数值」。

### ADR-020 单行横表独立成类 `kv_row`（2026-10-21）

- **决策**：`LogicalTable.kind` 增加 `kv_row`，并配两个字段 `pairs` / `orphan_values`。
  **不改变切分边界**——只细化已经切好的段落的类型标签。
- **背景**：三季报 P4_T06 首行是「报告期末普通股股东总数 | 642,600 | 报告期末表决权
  恢复的优先股股东总数 | 0」。它不是「一行数据」，而是同一行并排的两组键值对。
  按列取值会得到无意义的记录。
- **判据**：单元格语义交替（键=纯文本、值=含数字），两种形态：
  ① ``键|值|键|值…`` 全部配对；
  ② ``值|键|值|键…|值`` 剥离首个**孤儿值**后配对。
  **完整配对数必须 ≥2**。
- **孤儿值不放进 `rows`**，存于 `orphan_values`：既不污染数据行，也不丢失信息。
- **实测**：年报 324 张中 1 张（P109，3 对 + 1 孤儿）；三季报 18 张中 1 张
  （P4_T06，2 对）。
- **守卫（2026-10-21 修订）**：**父表已有表头时，绝不判 `kv_row`**。
  这是结构事实而非内容猜测——表若有列名，每行就是「按列取值」的数据行。
  原判据只靠「单元格是否含数字」区分键/值，遇到文本值列必然出错（见坑-22）。
- **失效条件**：仅「父表无表头」是必要非充分条件。若某张无表头的表里恰好有一行
  4 格「键|值|键|值」形态的普通数据行，仍会被误判。换公司需复核。

### ADR-022 跨页表的页码区间由「空 table 占位块」回填（2026-10-26）

- **决策**：`TableBlock` 增加 `page_end`；`content_list_to_pages` 在遇到空的
  `table` 块时，把它的页码回填给**上一张表**。表格仍然只在锚点页渲染一次。
- **背景**：MinerU 对跨页表格的处理是「把所有行合并进起始页那一个块，后续页各留
  一个空的 table 块」。原实现 `if not text.strip(): continue` 把这些空块直接丢掉，
  于是 `page_start == page_end` 恒成立——**19 张跨页表的页码区间全部失真**，
  最严重的 `P94_T57` 实际覆盖 P94–P103（165 行公告索引），却只标 P94。
- **为什么不能用别的方法**：
  - 锚点块的 HTML **不在每页重复表头**（165 个 `<tr>` 里表头只出现 1 次），
    数不出页数；
  - 按 bbox 高度除以行高估行数——折行行高不一致，必然错且无从核验；
  - 行级页码归属需要逐行定位，PDF 文本反查实测只有 57% 覆盖率，
    剩下 43% 会静默出错，比给一个诚实的区间更危险。
- **三条护栏**（`_extend_page_end`）：
  ① 必须已经有一张表；② 必须是**本页第一个** table 块——P65 形态是「页首空块
  续上一页的表、页中实块才是新表」，所以页内**第二个及以后**的空块不能算给上一张表；
  ③ 页码必须**紧接**上一张表的末页，断档说明中间另有内容。
- **实测**：19 张表回填成功，跨页物理表 3 → **22 张**；
  `table_id` 之外的 `parent_id` 变成 `#P94-P103_T57`，逻辑表号随之变为
  `#P94-P103_T57#S01`；逻辑表数仍 320、类型分布完全不变、14 条守恒律全过。
- **验证**：`data/reports/fix-page-span-年报.md` 逐张列出占位块页与 PDF 文本反查；
  **21/22 张有行能在区间内定位**，只有 `P72-P73` 全未命中
  （MinerU 把「公司的职工代表监事」写成「公司职工代表监事」，属内容差异不是区间错）。
- **失效条件**：MinerU 若哪天不再为跨页表留空占位块，回填会静默失效——届时
  跨页表数会掉回 3 张，`fix-page-span-报告` 的「跨页物理表」计数会立刻暴露。

### ADR-021 表格还原先做「网格化」，再识别多行表头（2026-10-23）

- **决策**：解析顺序固定为 **HTML → 网格（rowspan 进位 + colspan 展开）→ 多行表头
  判定 → 压平成一行**。表头不再假设「只有一行、且在第 0 行」。
- **背景**：中国年报的财务表大量使用双层表头（`2025年/金额`、`本年变动/追加投资`）。
  原实现 `header_offset = 1 if first_is_header else 0` 写死只吃一行，第二层被当数据行。
- **两个独立缺陷**：
  ① `rowspan` 只记录不展开，第二层表头整体左移一列（见坑-23）；
  ② 没有「多行表头」概念，第二层整行留在数据里（见坑-24）。
- **判据（R1/R2/R3，全部是 HTML 结构事实，不含从单份 PDF 数出来的阈值）**：
  - **R1** 当前层有 `colspan>1`，且不是「单格跨满全宽」——后者是表标题，抽成
    `table_title`，不占表头层。
  - **R2** 下一层的**自有**列 ⊆ 本层分组覆盖的列。自有 = 排除上一行 `rowspan`
    下发来的列（`_carried_columns` 复刻列游标算出），也排除原地重复上一层列名的
    列（MinerU 对没有 rowspan 的 stub 列会在两层都输出一遍）。
  - **R3** 下一层自有格无纯数值。
- **压平规则**：用 `/` 连接各层；含 `colspan` 的层按**原始单元格列区间**取值，
  否则 `快报产量/本报告期` 会退化成 `本报告期`，分组信息整层丢失。
  **首列为空时保留空串**——财务报表「项目」列表头经常留空，凭空填「项目」会让
  L1 拿到假列名。
- **数据结构**：`TableBlock` / `LogicalTable` 增加 `header_rows`（逐层原貌）与
  `table_title`；`header` 保留为**压平视图**，下游（Markdown 渲染、检索、L1）
  不需要感知层数。
- **实测**：年报 282 张非空物理表 → 232 张有表头，其中 **45 张是多层表头**；
  抽出 5 张全宽表标题；逻辑表 324 → **320**（4 张「表头单独成段」的假段并入下一段）；
  `kv` 8 → **4**（4 张双层表头表原来被误判为键值表）；14 条守恒律全过。
- **可移植性**：三条判据只用 HTML 结构，换公司、换版面都不失效；且不引入新阈值。
- **失效条件**：MinerU 自身 `colspan` 计数与内容不一致时（P128/P265 疑似），
  压平会出现分组列与叶子列对不齐。这类表需人工核对。
- **补充（2026-10-26）**：步2 落地时只把**压平字符串**送到了下游——
  `StitchedTable` 没有 `header_rows` / `table_title` 字段，`emit()` 主路径也没传，
  于是 320 张逻辑表的 `header_rows` 全是空（`_build_one()` 里虽写了，但它只在
  两个兜底分支被调用，实测从未执行，且引用了不存在的属性会直接 `AttributeError`）。
  修复：`StitchedTable` 补两个字段、缝合时从首块带过来、`emit()` 在
  `header_source == "inherited"` 时透传。修复后**50 张逻辑表**带多层表头原貌、
  **7 张**带表标题。这条教训写进坑-26。
- **补充二（2026-10-26）**：R2 原写「下一层的每个自有单元格都落在分组格覆盖的
  列区间内」，实测在 **P180「合营企业」表**上失效——MinerU 把 `本年变动` 的
  colspan 少算两列、行尾补了两个空 `<td>`，末两列的分组格就成了空串，这两个
  列不在任何分组内，整张表因此退化成单层表头。放宽为「只有**父格有名字却没被
  分组覆盖**的列才阻止判定」后恢复正常（`本年变动/追加投资` 等分组名回来了）。
  同一处还查清 `P192` 为何没修好：它的 `<td>本年增加</td>` **没有 colspan**，
  下一行才出现唯一的子项 `企业合并`——由此得到一条更直接的判据候选：
  **表头层数上限 = 表头行的 max(rowspan)**（`rowspan=2` 本身就是「这格跨两行」）。
  未实施。

### ADR-023 表格形态（data / kv）由「有效列数」判定，行数不参与（2026-10-26）

- **背景**：原 `kv` 判据是 `len(rows) <= 2 and all(无数字)`。它有两个毛病：
  ① 「≤2 行」是从这份 PDF 数出来的魔法数，5 行的「审计意见类型 | 标准的无保留意见」
  被判成 data；② 「无数字」把带日期/金额的键值表（`P117_T69`）挡在外面。
  用户确认了判据方向：**形态看的是「这张表有几列有效内容」**。
- **决策**：
  ```
  有效列数 = 有数据的列数 − 恒定填充列数
  ```
  - 有数据：该列在数据行里至少有一个非空取值（表头行不计）
  - 恒定填充列：该列非空取值 **≥3 个且全部相同**
  - `≥3 → data`；`=2 → kv`；`=1 → data`（单列标签组不构成键值表）
  - **行数完全不参与**；`summary` 判据优先于 `kv`；`kv_row` 仍限定单行并排
- **为什么阈值是 3**：2 个样本分不清「恒定」与「恰好相同」。实测 `P45_T30`
  （衍生品投资表 9 列）只有「外汇」「合计」两行有数字且两行完全相同，
  不设下界会把 8 个真数据列全剔掉，9 列变 2 列，误判成键值表。
  试过 3 与 4，结果完全一致——说明它是下界，不是待调的参数。
  另测过「短文本才剔」（取值 ≤2 字且非数字），只是减少剔除列数，不改结论。
- **实测（002594 2025 年报）**：逻辑表 320 → **317**（三张子段并回父表），
  `data 308 → 284`、`kv 4 → 25`；25 张里有 23 张原本就是 2 列、2 张靠
  「恒定填充列」判出来的（`P8_T01` 释义表的「指」列、`P75_T46` 只有 2 列有数据）。
- **已知失效情形**（换 PDF 前先想清楚）：
  1. 只有 2 行、且真的存在恒定填充列的表，剔不掉 → 会判 data；
  2. 恒定列本身是真实数据（如 58 行全是「无」），被剔后若总列数掉到 2 就会判 kv；
  3. 序号列算有效列 → 「序号 | 名称」这种会判 kv；
  4. 币种/汇率这类恒定元数据被剔——这正是想要的效果。
- **拒绝过的替代方案**：「每行恰好 2 个非空格 + 无数字」的结构规则。实测改判 4 张，
  **2 对 2 错**（错的正是 `P242` 两张关联方表），而且「无数字」会挡掉 P117_T69。

### ADR-024 可移植性：判据优先用「语义标签」，其次才是「统计量」（2026-10-27）

- **背景**：赛力斯年报一跑，三处判据立刻失效——汇总块全错、资产负债表恒等式
  找不到行、现金流差 30 元。复盘发现共性是：**这些判据的输入是「这份 PDF 的数
  学特征」（非空格数、行数、有效数字位数），而不是「中文报表的语义」**。
  比亚迪能满足只是因为它恰好长成那个样子。
- **决策**：新增或修改判据时，按这个优先级挑输入——
  1. **结构事实**（`colspan` 是否跨满、`rowspan` 是否跨行、列数是否相等、是否本页
     第一个 table 块）：换公司、换行业、换年份都成立，**首选**；
  2. **语义标签**（标签是否含「合计/小计/总额/总计」、是否以「注」开头、
     是否带中文序号）：中文财报的固定用词，跨公司稳定，**次选**；
  3. **统计量**（非空格数、行数占比、重复率）：只在没有 1、2 可用时才用，
     并且必须写清「失效时是会漏还是会错」——**漏可以接受，错不行**。
- **本条落地的三处**：
  - 汇总块：`后继行非空 ≤4` → `标签含 合计/小计/总额/总计`
  - 资产负债表：`同表内同时出现两个科目` → `_locate_row()` 按 `parent_id`
    就近 + 全文档兜底 + 科目别名表
  - 数值：`10 位有效数字` → 全精度解析，指纹单独归一
- **实测对比**（同一套代码，两份年报）：
  | | 比亚迪 2025 | 赛力斯 2025 |
  |---|---|---|
  | 改前 summary | 7 张（2 张误判） | 19 张（16 张误判） |
  | 改后 summary | 1 张（真汇总块） | 1 张（真汇总块） |
  | 改前守恒律 | 14/14 | 7 条过、1 条败 |
  | 改后守恒律 | 14/14（输出逐字未变） | 11/11 |
  | 逻辑表数 | 317 → 317 | 377 → 377 |
- **失效情形**：语义标签是中文报表的用词习惯，**英文/繁体/日文报表不适用**；
  遇到非中文语料必须回到「结构事实」这一层重新设计，不能照搬词表。

### ADR-025 超过 MinerU 页数上限时自动分批，并在内存里合成**一份** content_list（2026-10-27）

- **决策**：`finkb parse --auto-split` 按 `--max-pages`（默认 200）切页、逐批用
  `page_ranges` 提交，把每批的 `page_idx` 平移「本批起始页 − 1」后拼成**唯一一份**
  `content_list`，再走原有的转换/清洗/缝合链路。合并逻辑是纯函数
  （`merge_batches()` / `offset_content_list()`），离线可测。
- **背景**：MinerU 的 vlm 后端单文件上限 200 页（实测报错
  `number of pages exceeds limit (200 pages), please split the file and try again`）。
  比亚迪年报 268 页、赛力斯 224 页都超。此前靠手工：跑两次 `--pages`，再手改
  JSON 给第二批 `page_idx += 200`。
- **为什么必须合成一份而不是保留两批**：页码锚点、跨页缝合的「前一页最后一个
  块 + 下一页第一个块」、以及 `page_end` 回填，全部依赖**同一套连续页号**。
  两批各自成文，批边界上的表会被当成两张无关的表。
- **为什么不平移 `page_number` 块**：它的 `text` 本身就是绝对页码（如 `"202"`），
  只有 `page_idx` 是每批从 0 重编号的。
- **离线对账**（不烧额度）：用 `data/_s1` / `data/_s2` 两批真实产物跑
  `merge_batches`，与当初手工合并的 `content_list.json` 对比——块数 4017 = 4017、
  `page_idx` 分布完全一致、`content_list_to_pages` 得 224 页（1..224）；
  比亚迪两批合并得 268 页（1..268）。

### ADR-026 表外的「2025 年」期间标签收回到表上（2026-10-27）

- **决策**：表格前**紧邻**的、整块只有一个年份的文本块（`2025 年` /
  `2024 年 12 月 31 日`），记为 `TableBlock.period_label`，并透传到
  `StitchedTable` / `LogicalTable`；渲染时写进 `logical_tables/*.md` 的注释行。
- **背景**：MinerU 把「2025 年」「2024 年」输出成表格**前的独立文本块**。结果
  P167 的 `T94`/`T95` 两张表头逐字相同（`账面余额/金额`…），一个 `809,662`
  （2025）一个 `1,005,795`（2024），**表里没有任何东西说明自己是哪一年**。
- **影响面**：比亚迪年报 **39 处**期间标签，37 处能挂到表上；**9 组成对出现且
  表头完全相同**。赛力斯年报 **0 处**——它把年份写在表头里
  （`['', '2024', '2025', '同比']`），所以这条是**格式差异**，不是通用缺陷。
- **判据**：正则只认「年份（可带 12 月 31 日）」，不做内容推理；必须是该表之前
  的**最后一块**，且不能是页眉/页脚/页码（`prev_noise`）。
- **为什么不并进表头**：会污染列名（`2025年/金额` 这种已有两层表头的表会变成
  三层）；期间是**表的属性**，不是列名的一部分。
- **为什么不删掉表外那块文本**：删了 `page_anchored.md` 就少一行人类可读的语境，
  而渲染时并没有重复输出，不会出现两遍。
- **未覆盖的 3 处**：P191 / P204 的标签后面紧跟一个文本块（表头也被拆出去了，
  同类问题见 P242）、P207 的标签后面是提示语「其他综合收益发生额：」。
- **验证**：`data/reports/period-label.md`（37 张逐张 + 9 组配对 + 勾选框）、
  `fix-period-label-diff-年报.md`（41 张逻辑表，只多 `period_label` 一个字段）。


- **补充（2026-10-27，赛力斯回归后）**：两条判据都只认比亚迪的写法，赛力斯各撞一次。
  1. **期间区间**：原正则只认「2025 年」与「2025 年 12 月 31 日」，
     赛力斯写「2025 年 1—12 月」，于是 4 张表把期间当成了表名。
     加一条 `\d{1,2}\s*[—\-~至]\s*\d{1,2}\s*月` 分支接住。
  2. **币种单独成行**：原 `_UNIT_LINE_RE` 要求「单位：/币种：」前缀，比亚迪这样写；
     赛力斯先写「单位：元 币种：人民币」，再单独一行「人民币元」——第二行漏过去，
     7 张表的 caption 成了「人民币元」。加一条整块只由「币种 + 单位名」组成的分支，
     并补上「数量单位：」这个前缀（P207 把三个单位挤在一行）。
- **为什么没有被低估的量级骗过去**：比亚迪年报**一张都不触发**这两条新分支
  （回归 diff 0 张），说明它们接的是真实的写法差异，不是放宽阈值。
- **回归结果**（逻辑表）：比亚迪 `self 52 / text 17 / section 51 / heading 170 / adjacent 19 / missing 8`
  与改动前**逐项相同**；赛力斯 `self 31→35 / text 44→35 / heading 194→199`，
  12 张变化全部是预期的 8 张单位行 + 4 张期间标签。

### ADR-027 表外标题用五态 `caption_source` 记录，空值必须说明「为什么空」（2026-10-27）

- **决策**：新增 `TableBlock.caption` / `caption_source`（透传到
  `StitchedTable` / `LogicalTable`）。`caption_source` 取
  `self` / `text` / `heading` / `adjacent_table` / `missing` 五态；
  `caption` 只有后三态才为空。
- **背景**：表格上方那句「单项计提坏账准备的应收账款情况如下：」是 MinerU 输出的
  **独立文本块**，既不是章节标题（没有 `text_level`），也不是表内标题，转换时自然丢了。
  同一节里常有好几张表（P167 的 T94–T98 共用 section「（2） 按坏账计提方法分类披露」），
  **表外标题是唯一的区分**。
- **为什么不只是一个 `caption: str`**：空串无法区分「由标题命名」「紧跟上一张表」
  「被正文挡住」三件完全不同的事，下游会把它们当成同一种缺失。
- **判据**：从表格往前回溯，跳过页眉页码、空块、期间标签、单位/币种/编制单位行、
  目录行、复选框行；遇到表格/图片 → `adjacent_table`；遇到标题 → `heading`；
  遇到超过 80 字的正文 → `missing`；其余短句按「冒号收尾或含
  如下/情况/明细/构成/列示/结构/安排」分 `self` 与 `text`。
- **`text` 档为什么也存原文**：`公司前 5 大客户资料`「现有产能」没有冒号也没有提示词，
  但确实是表名。存下来标低置信，比当空值丢掉好。
- **实测**（逻辑表）：比亚迪 `self 61 / text 25 / heading 196 / adjacent 28 / missing 7`；
  赛力斯 `34 / 59 / 257 / 21 / 6`。`missing` 全部核实为「上方是成段正文」，不是漏判。
- **与表内标题的关系**：比亚迪 5 张、赛力斯 8 张自带 `table_title`，它们上方都是标题块，
  无一同时有表外 caption。真遇上时两个字段都保留、互不覆盖，
  展示顺序 `caption → table_title → section`。
- **验证**：`data/reports/caption-map.md`（两家 694 张全量，`text`/`missing` 逐张带勾选）、
  `fix-caption-diff-年报.md`。
- **补充（2026-10-27，按用户逐页裁定返工）**：三条判据被改写，第一条是**收回**：
  1. **删掉「跨页即 missing」**。它修好 P8，却误伤 P124（「后附财务报表附注为本财务报表的组成部分」
     在上一页，用户判定「可以切分在一起」）。真正区分 P8 的不是页码而是**形态**：
     「五、在香港…公布的公司 2025 年年报。」是中文编号名单中的一条，属正文列举 →
     新增 `_LIST_ITEM_RE = ^[一二三四五六七八九十]+、` 判 `missing`。
  2. **表单问句只看「是/否」且勾了「否」**。原来一律跳过复选框上方那句，误伤
     P62/P63/P72/P81（「适用 □不适用」上方那句**就是表名**）。MinerU 用私用区字形
     `\uf052` 表示勾选并紧贴被选项，故 `_BOX_NO_ANSWER_RE = "\uf052\s*否"`：
     勾「否」= 答案说「没有」，问句与下表无关（P11）；勾「是」= 下方正是被问的清单（P76）。
  3. **新增第六态 `section`**：分段自带 `section_path` 时不再沿用表级 caption，
     否则 P217_T205 的「与投资活动有关的现金」那段会继承「与经营活动有关的现金」。
- **返工后的实测**：比亚迪 `self 52 / text 17 / section 51 / heading 170 / adjacent 19 / missing 8`；
  赛力斯 `31 / 44 / 84 / 194 / 18 / 6`。用户逐页裁定的 17 张**全部与裁定一致**。
- **教训**：先按「结构差」加规则，再用用户的逐页裁定回归，比一次想清楚更可靠；
  两个守卫同时上线时，误伤数（5）大于修复数（2），**必须逐条回放再收**。

### ADR-030 L1 选表按内容而非章节；单位按公司推断（2026-10-29）

- **背景**：章节字段在 25 份语料里不可靠——有的写「二、财务报表」，有的被单位说明行
  覆盖成「（除特别注明外，金额单位均为人民币元）」；且一张物理表常被切成多张逻辑表
  （资产负债表最多 5 段），按标题挑会漏掉半个报表。
- **决策**：
  1. 判类与挑选都在**父表**层面做（内容锚点 + 行数），选中后整组输出它的逻辑子表；
  2. 只抽合并报表：资产负债表从第一张含「资产总计」的父表取到第一张含「负债合计/
     所有者权益合计」的父表；利润表/现金流量表取行数最多的一张；
  3. 记账单位按公司推断（主要会计数据与利润表的营业收入数量级比），
     主要会计数据一律按「元」入库。
- **代价**：依赖「合并在前、母公司在后」的排版惯例；同一文档内同 (期间, 指标)
  先到先得，主要会计数据优先于三张报表。
- **失效条件**：若某家公司母公司报表排在合并报表之前，或报表单位与主要会计数据
  不一致，需改成逐表声明单位，并从表外「单位：」行读取。

### ADR-032 列级召回 + 确定性修复 + 表内嵌表头拆分（2026-10-29）

- **背景**：逐字反查只能验「模型已输出」的数字，整列漏掉不会报错——601127 三季报的
  「2024 年前三季度」整列静默消失；银行「经营业绩 + 规模指标」把两段表头拼在一张表里，
  `2023年末` 的余额被当成 `2023H1`；模型偶尔返回空体或把 `metric_id` 写成 `metric`。
- **决策**：
  1. `missing_columns` 用关键行（营业收入/营业总收入/净利润/资产总计…）判断每一列有没有数；
     关键行匹配不上时退回「该列至少 3 个数值」。
  2. 缺列用 `only_cols` 补抽一次；仍缺则计入 `column_gaps`，不静默。
  3. 空返回 / JSON 解析失败带提示重试一次；`metric` 键统一归一为 `metric_id`。

  5. `split_header_blocks` 按表内嵌表头把一张表拆成多段，各用各的期间映射。
  6. 「2024年末 / 2023年末」按年份映射，不再一律当作当年期末。
- **代价**：重试与补抽让 LLM 调用数上升（单份 12–60 秒）；`repaired` 放宽了「模型必须指对行」，
  只限行标签匹配的场景。
- **失效条件**：若某行业关键行名与字典差异过大（如银行用「营业收入」之外的科目），
  召回判据需扩充；表内若出现与数据行同形的「表头」，拆分会误判。

### ADR-035 跨页报表按「页序 + 内容」拼块，不依赖章节标题（2026-10-30）

- **背景**：券商（中信证券）与能源（中国神华）的报表跨页切分，页标题只写日期/公司名，
  导致中信三表全部没选中（BS/IS 为空、CF 选到「主营业务分析」里的表）、神华 BS 缺第一页、
  CF 只选到「经营活动」半张。
- **决策**：新增 `_statement_runs`，按页序拼「同一张报表」：种子页看内容锚点

  IS 为空；CF 为空/缺投资或筹资活动/落在主营业务分析章节。

  20,819.03 亿 = 负债 17,560.80 + 权益 3,258.22；神华 BS P147-151、CF P160-163，

### ADR-036 多年度摘要表不当期报表；被排除后用整块拼回续页（2026-10-30）

- **背景**：神华年报里有两张利润表候选：P155 是当期法定表（2025/2024 两列），
  P301 是五年摘要表（2021–2025 五列，章节却写「合并利润表」）。旧规则取行数最多，
  选中的是摘要表，于是 2021/2022 两个年度被当成当期事实入库；而 P155 本身只到

  补回「归属于母公司股东的净利润」等行；③ `_best_run` 对多年度块记 -1000 分，

### ADR-037 三表单位用「与 summary 同科目比值」反推（2026-10-30）

**背景**：全量重灌 29 份时发现两类单位误判——比亚迪 2025 年报 summary 用元、三表用千元；
长城 2025 年报 summary 用万元、资产负债表用元。旧规则（ADR-031/034）只有「表头/行标签 →
页面正文 → 文档级推断」三级来源：页面正文的「单位：元」可能来自同页附注表，不能直接套到
报表；文档级推断只能判断相对差异，无法判断绝对量级。

**决策**：`write_document` 先确定 summary 的单位（表头 → 行标签 → 该页正文），再取 summary
与三表中**同一 metric**（优先 revenue、total_assets、net_profit、ocf）的数值比，反推三表单位：
`目标单位 = summary 单位 / (三表值 / summary 值)`，结果必须落在 元/千元/万元/百万元 的 10%
以内，否则放弃并退回页面或文档单位。没有 summary 的文档（如中国平安半年报）不做推断。

**代价**：假设同一文档的三表共用一种单位；若资产表与利润表单位不同，会被统一成一种。

**失效条件**：同一文档内三表单位不同；或 summary 与三表没有共同 metric（此时退回页面单位，
可能再次踩附注表的坑）。

### ADR-031 季报期间按「流量/存量」分标签；记账单位按文档推断（2026-10-29）

- **背景**：季报里「本报告期」是单季、「年初至报告期末」是累计；三季报利润表只写
  「本期发生额」，实际口径是 1–9 月累计。混用会把单季当累计。另：002594 年报用千元、
  季报用元，公司级单位假设不成立。
- **决策**：流量（利润表/现金流量表/主要会计数据）用 `2025Q1`、`2025Q1-Q3`、
  `2025Q3`（单季）三个标签；存量（资产负债表）用期末时点 `2025Q3`。单位先在

  需要按表头显式日期重新映射。

### ADR-038 语义验收用「金标事实集」，不看 exact 率（2026-10-30）

**背景**：`match_level=exact` 只证明「数字抄对了单元格」，不证明「抄的是要的那个数」。
2026-10-30 一天内就出现三次 exact=100% 却错的情况：神华选了五年摘要表、美的 summary
单位差 1000 倍、601127 的 2023 负值整列被当注释跳过。只看条数和未匹配数，这些错都不会报警。

**决策**：建一份 72 条的金标事实集（3 家车企 × 8 个指标 × 3 个年度）：
`config/gold_facts.yaml` 记录公司/期间/指标/期望值/来源文档/页码；期望值从 **PDF 文本层**
人工抄录（PyMuPDF），与 MinerU 解析链路独立。`tools/gold_check.py` 按
`source_doc + period + metric_id` 查 `facts`（不用 dedup，避免重述混入），容差 0.01；
`scripts/check.sh` 在 `data/facts.duckdb` 存在时自动跑，失败即退出 1。

**代价**：只覆盖 3 家 8 指标，不是全量证明；新增公司/指标要同步扩表；金标本身也可能抄错，
所以每条都带页码，可回原文复核。

**失效条件**：更换 PDF 版本或公司重述导致期望值变化；指标口径（合并/归母）调整；
金标与抽取代码共用同一来源时，必须先复核来源再信结果。

### ADR-039 表内第二段表头按「行分段」定期间（2026-10-30）

**背景**：一季报的「主要会计数据」常先写「本报告期 / 上年同期」，中间再插一行
「本报告期末 / 上年度末」，后半段的余额语义与前半段不同。按整表列映射会把
上年度末的余额标成上年同期：002594 2026 一季报的总资产 8837 亿被记成 2025Q1，
而 2025 一季报的真实值是 8405 亿。

**决策**：`_is_subheader` 识别「首格为空、其余格无数字且含期末/年末」的行；
`_annotate_periods` 按行所在段覆盖 Observation 的 period；`column_periods` 增加
「上年度末 → 上一年」的映射。`verify` 优先用 observation 自带的 period。

**代价**：段头识别是启发式；表格中间若有无数字的说明行且带「期末/年末」字样，可能误分段，
但需要首格为空 + 至少两个这样的格，误判概率低。

**失效条件**：第二段表头不含「期末/年末」等词（如只写「2026年3月31日」）；
或同一行既有段头又有数据。

### ADR-040 指标字典冻结为 v1，版本与哈希随库落盘（2026-10-30）

**背景**：字典文件此前只有一行「v0」注释，库里没有任何版本信息。改一个别名或口径，
旧事实不会重算，新旧事实混在一起也看不出来；L2 写知识页时更无法声明「这页基于哪版口径」。

**决策**：
- `config/metric_dict.yaml` 顶层加 `version: 1`、`frozen_at: 2026-10-30`；
  改任何 `metric_id / metric_name / aliases / unit_default` 都必须升版本并重灌。
- `load_dict_meta()` 返回版本、冻结日期、文件 sha256。
- `FactStore` 新增 `meta(key, value)` 表与 `set_meta/get_meta/all_meta`。
- `ingest_documents` 开始时写入 `metric_dict_version`、`metric_dict_sha256`、
  `metric_dict_frozen_at`、`llm_model`、`built_at`。
- 唯一库补写 meta，并把 21 项字典载入 `metric_dict` 表（此前该表是空的）。

**代价**：版本号靠人守，代码不会阻止你改字典却不升版本；meta 只记录最近一次 ingest，
不能表达「一个库里混了两版」。

**失效条件**：如果以后按行业拆多套字典或需要并存多版本，单版本号不够，要改成
「字典 ID + 版本」并允许 facts 带 dict_id。

### 坑-63 manifest 缺行时公告日期静默变成「入库当天」

**症状**：唯一库里 7 份文档的 `report_date` 是 2026-10-30（入库日），其余 22 份正确；
`facts_dedup` 的「按公告日期取最新」对这 7 份失效。

**根因**：这 7 份是后来补充的语料，没有写进 `raw/manifest.csv`；`ingest.py` 在
manifest 查不到时用 `date.today()` 兜底，且不告警。

**修复**：补 7 行 manifest（5 份公告日取自巨潮接口，中信/广汽按 PDF 生成时间与
董事会日期推定并在备注写明），再把库里这 7 份的 `report_date` UPDATE 为正确值；
校验后全库无 2026-10-30 的兜底日期。新增文档时必须同时写 manifest——这是硬约束。

**教训**：兜底值不能静默。查不到公告日期应写进 meta 的告警计数或直接报错。

### ADR-041 「来源数」按证据层计：L1 事实库与 L0 原文各算一个（2026-10-31）

**背景**：L2 的 draft 隔离规则是「来源 <2 的页面进 `_draft/`」，但 Summary 按设计
「每份年报一份」，天然只有一个 L0 原文来源。照字面执行，所有 Summary 永远转不了正，
验收标准「来源 <2 的页面停在 `_draft/`」会退化成「所有页面都停在 `_draft/`」。

**决策**：来源按**证据层**计数，而不是按文件数。`sources` 至少包含两项：
`l1:facts#<company>`（L1 事实库）与 `l0:<doc_id>`（L0 页码锚定原文）。lint 统计
`l1:` 与 `l0:` 两个前缀是否都存在；概念页跨公司时追加多个 `l1:facts#...` / `l0:...`。

**代价**：同一层的多份文档仍只算一个来源；「两个来源」不等于「两份独立证据」，
只保证页面同时有数值底座和原文锚点。

**失效条件**：若以后允许只凭 L1 生成纯财务对比页（没有原文叙述），需要把规则改成
「来源层数 ≥1 且每条 claim 都有出处」，而不是强制两层。

### ADR-042 lint 规则 4 只检查 `wiki_scope.yaml` 登记的文档（2026-10-31）

**背景**：P8 规则 4 要求「`raw/` 下每份文件都要有对应 wiki 条目」。MVP 只编译
`002594_2025_年报` 一份，`raw/` 有 29 份，第一次跑 lint 就会报 28 条「缺条目」，
验收要求「lint 零错误」不可能达到。

**决策**：新增 `config/wiki_scope.yaml`，列出当前要编译的文档。规则 4 只检查
登记文档的 `summaries/<doc>.md` 是否存在；未登记文档只统计数量、不报错。
新增语料入库时必须同步登记，否则永远不会被编译——这是流程约束，不是代码约束。

**代价**：漏登记的文档不会报错，只能靠入库流程守。

**失效条件**：全量编译 29 份后，把规则 4 改回全量检查，并删掉 `wiki_scope.yaml`
或让它只表达「优先级」。

### ADR-043 锚点校验用 `report.json` 页数，不再依赖 `sources/<doc>.json`（2026-10-31）

**背景**：P8 规则 8 原本要求 `[Ref: doc#P{n}]` 能在 `sources/<doc>.json` 里 O(1)
定位。但 ADR-029 已决定 L1 不产出按页 JSON（P6 选 B），规则 8 的依赖悬空；P5 骨架
里的 `sources/` 目录也一并作废。

**决策**：锚点校验改为：
- `data/parsed/<doc>/report.json` 的 `pages` 字段是整数总页数；
- `1 ≤ n ≤ pages` 即认为锚点合法；
- 同时要求 `page_anchored.md` 里存在 `"page": n` 的 META 块，防止页数对但正文缺页。
- 不校验「这一页真的有这句话」；引文类数字由 `quote` claim 单独校验（ADR-044）。

**代价**：锚点可能指向一个真实存在但与叙述无关的页。这类错误只能靠 quote claim
的原文匹配和人工抽检发现，规则 8 本身管不了。

**失效条件**：若以后需要字符级定位或「页内哪一段」的锚点，必须回到按页 JSON，
并重写规则 8。

### ADR-044 页面数字用「正文 + 脚注 + claims 表」，三种 claim 各自可验（2026-10-31）

**背景**：§9.4 只定义了结构化 claim `{claim_text, anchor, metric_refs[]}`，但页面
正文是 Markdown。不定一种落地写法，规则 9 无法检查「数字有没有出处」，也守不住
「数字只由 SQL 计算」这条核心不变量。

**决策**：
- 正文写正常数字，数字后跟脚注标记 `[^cN]`；脚注定义由代码生成，不允许 LLM 写。
- `data/wiki.duckdb` 的 `claims` 表是唯一真相，三类：
  - `fact`：`fact_id` 指向 facts 行，显示值必须等于该行按单位格式化的结果；
  - `query`：`query_id + params` 指向 `config/wiki_queries.yaml` 的命名 SQL，lint 重跑比对；
  - `quote`：`anchor` 指向原文页，显示的数字字符串必须能在该页 `page_anchored.md` 找到。
- lint 规则 9：正文每个数字必须被同一句的 claim 覆盖；年份、`[Ref: ...#P{n}]` 页码、
  标题序号走白名单；脚注与 claims 必须一一对应。
- LLM 编译时只输出 `{{cN}}` 占位符，数字由代码渲染——LLM 碰不到数字。

**代价**：脚注增加阅读噪声；`quote` 类依赖原文数字字符串的字面形式（全角/千分位
需要归一化）。

**失效条件**：若 Obsidian 的脚注渲染不可接受（比如导出 PDF 时脚注挤在一起），
退回「正文占位符 + 独立渲染层」，claims 表不变。

### ADR-045 指标字典升 v2，新增 `segment_facts` 承载分产品结构（2026-10-31）

**背景**：探针 02（分产品结构）与 05（现金流与资本结构）需要的口径在 v1 字典里
没有：投资/筹资现金流净额、短期/长期借款、应付债券、租赁负债、销售/管理/财务费用、
流动资产/负债、应收账款；分产品收入/成本/毛利率则完全不在 facts 的键里。

**决策**：
- `config/metric_dict.yaml` 升 `version: 2`，新增 13 项指标，仍只收「财报直接披露」
  的科目；毛利率、资产负债率、有息负债、流动比率、费用率、同比继续由 SQL 视图算，
  不进字典。
- 新增 `segment_facts` 表：`(company, period, dimension, segment_name, metric,
  value_norm, unit, source_doc, page_num, table_id)`。`dimension` 取 `product` /
  `region` / `industry`，分产品表选「同时有营业收入、营业成本、毛利率」的那张。
- 字典升版本必须全量重灌（ADR-040），重灌后 `gold_facts` 扩到覆盖新指标。

**代价**：重灌 29 份（实测约 6 分钟、几美分）；分产品表在不同公司列集不同，选表
规则需要金标兜底；`segment_facts` 与 `facts` 的合计可能有尾差，需定容差。

**失效条件**：若多数公司只按行业披露、不按产品披露，`dimension` 需要允许为空或
改为通用「分部」表，不能假设每家公司都有 product 维度。

### ADR-046 关系从结构化表格抽；矛盾先做 facts 级跨文档检测（2026-10-31）

**背景**：`relations` 表建了但 0 行；L2 的「实体关系图」「证据依赖图」和 `contradicts`
链接都没有数据来源。矛盾检测也没有任何机制。

**决策**：
- `relations` 只从结构化表格抽：主要子公司（`subsidiary_of`）、关联方交易
  （`related_party_of` + 金额）、前十名股东（`shareholder_of` + 持股比例）、
  对子公司担保（`guarantees_for`）。每条边带 `source_doc + page_num`。
- 表加 `attrs_json` 存金额/比例等属性；`src_type/dst_type` 取 `company` / `entity` / `person`。
- 矛盾先做 facts 级：同一 `company + metric_id + period + caliber` 在不同文档里
  `value_norm` 不一致 → 写 `conflicts` 表，带两边的 `fact_id`。
- 不做：客户/供应商名单（只披露前五名合计）、文本语义级矛盾（需要 LLM 判断）。

**代价**：关系覆盖受限于有结构化表的公司；客户/供应商实体缺失；矛盾只覆盖数值，
不覆盖叙述冲突。

**失效条件**：若 L3 需要客户/供应商实体或「正文说法与表格数字矛盾」，必须引入
文本抽取或外部数据，`conflicts` 的表结构也要能存 claim 级冲突。

### ADR-047 派生比率走命名 SQL（query claim），LLM 不得自算（2026-11-01）

**背景**：批量编译时模型直接写出了「17 个百分点」「28.9%」「76.1%」「4.7%」——
都是它自己拿目录里的数字现算的。这违反 ADR-001（数字只由 SQL 计算），也让 R9
对不上账（claim 里没有这个数）。

**决策**：
- 毛利率 / 净利率 / 研发强度 / 资产负债率等派生值，在 `config/wiki_queries.yaml`
  里定义成**命名 SQL**，编译时由 `_try_add_query` 查库写入 claim 账本，正文只能引用占位符。
- `SYSTEM_PROMPT` 增加硬规则：不得自行计算差值/增速/占比/百分数/合计；叙述差异用
  「明显高于/低于」；占位符必须写双花括号 `{{cN}}`。
- 查不到结果时跳过（银行没有「营业成本」，毛利率天然不存在），不编造。

**代价**：比率口径被 SQL 固定下来，新增比率必须改 YAML；模型措辞自由度变窄。

**失效条件**：若未来允许「仅用于叙述的口算」（不落 claim、不进正文数字），需先证明
它能通过 R9 的数值对账，否则不允许。

### ADR-048 同一逻辑页的草稿与旧 active 不得并存（2026-11-01）

**背景**：重编某文档时新正文进了 `_draft/`、旧页面还在正式目录。lint 按逻辑页名读
的是**正式目录**的旧正文，却配新 claims，于是报「claim c16 没有脚注定义」——
问题在错的地方，真正的原因是新页面没过门禁。

**决策**：编译流程改为「写草稿 → 写 claims → **先删同名旧 active** → `page_issues`
校验草稿 → 通过才转正」。`concepts.py` 同样处理。删除原先「失败后才删旧 active」的代码。

**代价**：校验期间正式页面短暂消失；若进程被 kill，需要重跑该页（可由 lint 发现）。

**失效条件**：若将来需要「新旧版本并存审计」，应改用版本目录而不是同一路径。

### ADR-049 定性页锚规则 R10 只报警告，且豁免三类文本（2026-11-01）

**背景**：方案 §9.4 要求「定性主张必须有 anchor」，但页面上有不少无需锚点的文本：
页面级说明（「本页…」）、表格引导语（「…如下：」）、实体页的关系索引条目。

**决策**：R10 `rule10_narrative_anchors` 检查「既无 claim 脚注、也无 `[Ref: doc#Pn]`」
的正文段落，severity 固定为 `warning`；豁免：标题/表格/代码块/脚注定义/加粗小标题、
`本页` 开头的说明、`如下：` 结尾的引导语、`type=entity` 的页面。转正门禁只拦 `error`。

**代价**：定性锚点缺漏不会阻止转正，只能靠 lint 报告人工看。

**失效条件**：若某天要求「零警告才允许合并」，把 R10 提为 error 并清掉豁免。

### ADR-050 批量编译 29 份，按文档独立编译、共用 claims 账本（2026-11-01）

**背景**：单文档 MVP 的编译器把页面标题写死「年报摘要」、期间取
`doc_id.split("_")[1]`、公司名取股票代码，半年报/季报会编出错误标题和错期数据。

**决策**：
- `selector.doc_period(doc_id)` 统一期间映射（年报→year、半年报→yearH1、一季报→yearQ1、三季报→yearQ3）；
  三季报流量指标优先取「年初至报告期末」（Q1-Q3），存量指标取 Q3（`_period_choices`）。
- 标题用 `公司名 + 年份 + 报告类型`（`report_kind`），公司名从 `raw/manifest.csv` 取。
- 批量脚本 `finkb/.tmp/batch_compile.py` 读 `wiki_scope.yaml` 逐份编译，写日志与结果 JSON，
  结束统一 `rebuild_index`；47 份/29 份的 claim 账本共用一个 `data/wiki.duckdb`。
- 结构页（分产品 Structure）只在有 `segment_facts` 时编译，否则 `skipped`。

**代价**：约 1338 秒、29 × 4 次 LLM 调用；同一文档重编不幂等（正文重写、claims 重写）。

**失效条件**：语料扩到几百份时应改为增量编译（按 `pipeline_fingerprint` + 页面 mtime 判断）。

### ADR-051 探针扩展只做方案已定义的 01–05；海外收入复用分地区 segment claims（2026-11-01）

**背景**：§7.3 写「二期扩到 8 个（01–07 + 风险展望）」，但方案只有编号，v3 §4 只定义到 05；
03（研发投入）、04（产能出海）有语义，06/07/08 没有定义。

**决策**：
- 只补 **03 研发投入**（`rd_expense` + `rd_ratio` 命名 SQL）与 **04 海外收入**
  （分地区表中境外口径的 `segment_revenue/segment_cost/segment_gross_margin`，直接作为
  segment claim，带页锚与 `l1:segments` 来源）。
- 试过给海外收入加命名 SQL 查询，随后删除：query claim 不带页锚，海外页凑不够
  l0 + l1 两层来源；且与 segment claim 数值重复。
- 06/07/08 不自行编造语义，留给二期/用户定义。

**代价**：海外页只出现在有分地区披露的 11 份文档；研发页在无研发费用的 21 份季报/银行文档 skipped。

**失效条件**：用户给出 06–08 定义，或语料补了「海外销量/分国家」披露时，本 ADR 需要重写。

### ADR-052 四层本体栈落地 DuckDB，只做校验不做推理（2026-11-02）

**背景**：目标要求「一个具体财务指标能构建出从本体到具体的层层链条，可追溯、可修改、
可被检索和机器阅读」。参考了两处标准：金融本体 FIBO（EDM Council）与财政部 CAS 2015
《企业会计准则通用分类标准》。

**决策**：

- 四层概念栈写进 `config/ontology.yaml`（55 个概念：L0 元概念 7 / L1 科目骨架 8 /
  L2 国标科目 34 / L3 派生指标 6），由 `tools/build_ontology.py` 生成。**YAML 是单一真相源**，
  DuckDB 只是它的投影；手工改库会在下次 `load` 时被覆盖。
- 落 DuckDB 四张表：`concepts` / `concept_relations` / `ontology_constraints` /
  `dimension_members`。表名用 `ontology_constraints` 而非 `constraints`——后者是 SQL 关键字。
- L1 借 FIBO 的语义骨架（`cmns:MonetaryAmount` / `fibo:Asset` / `fibo:Income` /
  `fibo:OwnersEquity` / `fibo:CashFlow`），只借类名与 `is_a` 关系，**不下载其 RDF**：
  实测闭包 20 个文件 / 291 个类，与我们相关的不到 10 个，其余是合同、地址、法人能力。
- L2 对 CAS 2015 自动对齐：每个 L2 的 `basis_element` 必须真实存在于从 label linkbase
  抽出的 4317 个元素表里，`tests/test_ontology.py` 守住这条——这是整条链的地基。
- **只校验不推导**：约束失败只报告，绝不自动修正事实（§7.5.6）。
- 链条六跳：概念 → 标准定位 → 祖先链 → 约束 → 事实 → 证据（页码 / 表号 / 原文命中）→ 页面引用。

**代价**：`concepts` 与 `metric_dict` 有冗余（靠 `metric_id` 关联）；CAS 引用的是 2015 版
（IPO 口径），新准则科目只能记 `basis=self` 并标注版本有效期。

**失效条件**：语料到 H 股 / IFRS 报表，或概念数破千导致递归 CTE 遍历变慢时，需重新评估
是否引入图存储。反过来说：只要概念数在千以内且只做校验，DuckDB 单库足够。

## 6. 被推翻 / 废弃的方案（不要重提）

## 7. 踩过的坑与护栏（防止回归）

每条都是**真实踩过**的，修复后有对应测试。改动相关代码前请先读这一节。

> 其中与 PDF 解析、表格结构还原、跨页缝合、表内切分相关的内容，已按主题重新组织
> 到 [`PDF解析细节.md`](./PDF解析细节.md)，那里有更完整的现象描述与判定规则速查。
> 本节保留原始记录（含坑-NN 编号），作为追溯依据。

### 坑-01 跨页表头会被误判成页眉清掉
- **症状**：缝合后表格没有列名。
- **根因**：跨页续接表在每页都重复表头，签名频次很高，被统计判定为「运行页眉」。
- **修复/护栏**：`line_signature()` 对以 `|` 开头的行直接返回 `None`；
  `_candidate_lines()` 只考察非表格块。
- **测试**：`test_signature_rejects_table_row`、`test_repeating_table_header_is_not_stripped`

### 坑-02 小文档上比例阈值退化为 1
- **症状**：只出现一次的正文行被删。
- **根因**：`int(3 * 0.3) = 0`、`int(5 * 0.3) = 1`，阈值失效。
- **修复**：`max(2, ceil(total_pages * min_ratio))`。
- **测试**：`test_single_occurrence_signature_is_not_noise`

### 坑-03 单文本块页面重复计数
- **症状**：幂等性测试失败——第二次清洗又删了 3 行。
- **根因**：整页只有一个文本块时，头部行与尾部行取自同一块，同一行被计两次，
  阈值被虚高。
- **修复**：`_candidate_lines()` 对候选行按内容去重。
- **测试**：`test_strip_is_idempotent`

### 坑-04 页眉清掉后页码残留
- **症状**：`剥离 268 行`看着正常，但抽查 P44 发现首块仍是 `"44 \n债券 019742…"`。
- **根因**：页眉是「文字 + 页码」两部分，签名只匹配文字部分。
- **修复**：新增页码行识别（ADR-013）。
- **测试**：`test_standalone_page_number_line_is_stripped`、
  `test_page_number_on_separate_line_is_stripped`

### 坑-05 页码作为独立块时清不掉
- **症状**：MinerU 路径测试失败，P41 页码块仍在。
- **根因**：独立页码块既不是页首块也不是页尾块，落在边缘区外。
- **修复**：增加「整块只有一个非空行」的放行条件。
- **测试**：`test_page_number_as_separate_block_is_stripped`

### 坑-06 「文本 + 表格」同块时表格消失
- **症状**：表格凭空不见。
- **根因**：整块被判为 `text`，表格行被吞。
- **修复**：`_segment_block()` 按行切分成 text 段与 table 段。
- **测试**：`test_text_before_next_table_blocks_stitching`

### 坑-07 无 META 的 Markdown 整篇丢失
- **症状**：解析出 0 页。
- **根因**：`flush()` 在 `current_meta is None` 时直接返回。
- **修复**：回退到 `default_doc` 第 1 页。

### 坑-08 MinerU 标题检测字段用错
- **症状**：`section` 继承链失效，所有标题被当正文。
- **根因**：content_list 里标题是 `type="text"` + `text_level` 字段，
  **正文块完全没有 `text_level` 这个字段**（不是 null/0）；`type="title"` 是
  layout.json 的写法。
- **修复**：`_is_heading()` 判断 `text_level is not None`。

### 坑-09 MinerU 跨页续接表被当成有表头
- **症状**：缝合拒绝拼接。
- **根因**：HTML → Markdown 往返强行给无表头表套表头（ADR-012）。
- **修复**：`html_table_to_rows()` 按 `<th>` 存在性返回 `(rows, first_row_is_header)`。

### 坑-10 上传预签名 URL 时带了 header
- **症状**：HTTP 403 `SignatureDoesNotMatch`。
- **根因**：OSS 预签名校验要求 **PUT 不带任何请求头**（含 `Content-Type`）。
- **修复**：`upload_file()` 显式不传 headers。

### 坑-11 分页解析时物理页码全错
- **症状**：`--pages 43-44` 解析出的表，`parent_id` 是 `#P1_T02` / `#P2_T03`。
- **根因**：MinerU 在只解析部分页时，返回的 `page_idx` **从 0 重新编号**；
  我们按 `page_idx + 1` 计算物理页码，得到的是「第 1 页」而不是第 43 页。
- **后果**：若不修正，**所有 `[Ref: doc#P1]` 锚点都会指错页**——对
  「物理页码强溯源」是致命错误。
- **修复**：MinerU 会输出 `type="page_number"` 的块，其 `text` 就是真实物理页码。
  `_build_page_number_map()` 建立 `page_idx → 物理页码` 映射，优先使用它；
  缺该块时才退回 `page_idx + 1`。
- **测试**：`test_page_number_type_overrides_renumbered_page_idx`、
  `test_page_idx_used_when_page_number_missing`

### 坑-12 MinerU 用 `<td rowspan>` 做表头，不用 `<th>`
- **症状**：P43 证券投资表明明有表头，却报 `header=无`。
- **根因**：ADR-012 当初假设「首行有 `<th>` 才是表头」。**实测 MinerU 的表头是
  `<td rowspan="2">`**，全表没有一个 `<th>` —— 该判据在真实数据上完全失效。
- **修复**：增加兼容判据——首行所有单元格 `rowspan≥2` 时也认定为表头。
- **测试**：`test_rowspan_merged_header_is_detected`
- **教训**：ADR-012 的「不走 Markdown 往返」结论仍然正确，但「按 `<th>` 判定」
  这一半是**错的**。设计决策要标注验证来源，未实测的假设必须显式标记。

### 坑-13 `rowspan` 未展开时留下全空垃圾行
- **症状**：P43 表多出一条全空行，`rows_count` 比实际多 1。
- **根因**：`<td rowspan="2">` 占两行，但 MinerU 在第二行仍输出 1 个空 `<td>`。
  解析器不展开 rowspan，于是这条空行被当成数据行。
- **修复**：`html_table_to_rows()` 剔除全空行，并同步维护 `row_has_th` /
  `row_spans` 的下标映射。
- **测试**：`test_rowspan_artifact_empty_row_is_dropped`

### 坑-14 `colspan` 未展开导致合并表列错位
- **症状**：缝合后表格看着「行数对、列数对」，但 P44 的数值整体左移 2 列。
- **根因**：vlm 用 `colspan="3"` 表示「这一格横跨三列」。解析器不展开时，
  一个 cell 被当成一列，其后的所有数值就整体前移。
- **危害等级**：**比缝不上更高**。缝不上会报错，错位则是**静默产出错误数据**，
  一路流进 L1 事实层。
- **修复**：`_HTMLTableExtractor` 展开 `colspan`，被跨越的列补空字符串占位。
- **测试**：`test_colspan_is_expanded_to_keep_column_positions`、
  `test_stitched_rows_have_uniform_width`

### 坑-15 vlm 的表头不做任何标记
- **症状**：`header=无`，表头行被当成数据行，`rows` 多 1。
- **根因**：vlm 的表头是普通 `<td>`，既无 `<th>` 也无 `rowspan`——
  ADR-012 的两条判据同时失效。
- **修复**：增加保守统计判据——**首行没有任何「纯数值」单元格、且第二行至少有一个**
  时判为表头。实测校验：P43 首行 14 个中文列名（0 纯数值）→ 表头；
  P44 续接表首行含多个金额 → 不判表头。`2025年` 这类带数字但非纯数值的单元格
  不会干扰判定。
- **测试**：`test_vlm_style_header_inferred_without_th_or_rowspan`、
  `test_data_row_is_not_inferred_as_header`、`test_header_with_year_label_is_still_header`

### 坑-16 分批解析合并时 `page_idx` 冲突
- **症状**：268 页合并后只解析出 **200 页**，且前 68 页的锚点被错映射到 201-268。
- **根因**：**每一批**的 `page_idx` 都从 0 重新编号。直接拼接 content_list 会让
  批次2 的 `{0:201, 1:202...}` 覆盖批次1 的 `{0:1, 1:2...}`，页码映射互相踩踏。
- **修复**：合并时把后续批次的 `page_idx` **整体加上前序批次的最大值 + 1**，
  使 `page_idx` 全局唯一；`page_number` 块的值保持不变（它本来就是真实物理页）。
- **已修（2026-10-27）**：`finkb parse --auto-split` 自动切批并调用
  `merge_batches()` 合成一份 content_list，见 ADR-025。手工合并已成为历史路径。

### 坑-17 拒绝理由误导排查方向
- **症状**：P72→73 的续接表**自带表头**（`姓名/职务/报告期初持股数…`），
  却报「列数不一致（6 vs 5）」。被这个理由带着去研究「如何修列数」，
  而正确答案是「它本来就是新表，不该缝」。
- **根因**：判据把所有检查压成一个 `bool`，且**列数比较排在表头判断之前**，
  于是最早失败的那条成了唯一可见的理由。
- **修复**：改为三态判定，表头检查前置。见 ADR-017。
- **测试**：`test_new_table_reason_is_not_column_mismatch`

### 坑-18 缺少「表结束」信号制造无谓告警
- **症状**：6 条告警里 4 条（P65/P132/P214/P229）的起始表都以
  「合计」「资产总计」收尾——表明明已经完整，却还在尝试往后缝。
- **根因**：只做结构判定（位置 + 列数），没有利用财务表的语义结束标志。
- **修复**：`stop_on_total_row`，命中即静默终止，**不记告警**。
- **测试**：`test_table_ending_with_total_is_not_stitched`、
  `test_total_marker_variants_all_stop_stitching`、
  `test_total_row_only_counts_last_row`、`test_stop_on_total_row_can_be_disabled`

### 坑-19 期间表头识别失败，导致列语义整体丢失
- **症状**：P137 现金流量表 `header=无`，`2025年/2024年` 被当成一条数据记录。
- **根因**：表头推断要求「次行含纯数值」，但这张表的第二行是纯文本的
  「一、经营活动产生的现金流量:」。判据在第二行就断了。
- **危害**：**比切分问题严重**——即使不切分，L1 也拿不到期间语义。
- **修复**：向前探测 3 行 + 全宽单格护栏 + 冒号列名兜底（ADR-019）。
- **测试**：`test_period_header_detected_by_lookahead`、
  `test_fullwidth_single_cell_is_not_a_header`、
  `test_colon_terminated_first_row_is_header`

### 坑-20 MinerU 对同一语义的分节标题给出两种编码
- **症状**：P137 只识别出 1 个分节点（「三、筹资活动…」），漏掉「一、经营活动…」
  和「二、投资活动…」。
- **根因**：同一个表格里，「一、」「二、」是 3 个普通 `<td>`（后两格空），
  而「三、」是 `<td colspan="3">`。只认 colspan 会漏掉前两个。
- **修复**：切分器增加第二类候选——「仅首列非空 + 标题形态（冒号结尾或中文序号）」。
  实测新增 20 处候选，全部是真分节标题。
- **测试**：`test_narrow_table_splits_on_numbered_heading`、
  `test_looks_like_heading_variants`

### 坑-21 「至少 2 组配对」这条约束不能省
- **症状**：最初按「单元格数偶数 + 键值交替」判定横表，年报里把
  ``房屋及建筑物 | 41,744,687 | 尚未办完所有手续`` 也匹配上了。
- **根因**：那是「未办妥产权证书的固定资产」表的一行数据（项目/账面价值/原因），
  只有 1 组完整配对 + 1 个悬空键。纯交替判据无法区分。
- **修复**：要求完整配对数 ≥2，且非空格数 ≥4。反例被排除。
- **教训**：**先扫描全量再定判据**。这条反例是扫描阶段发现的，不是上线后。
- **测试**：`test_three_cell_row_is_not_kv_row`

### 坑-22 「值必含数字」的假设不成立
- **症状**：`_cell_kind` 把「尚未办完所有手续」判为**键**，而它是
  「未办妥产权证书的原因」列的**值**。P186_T134 的三个单元格
  ``房屋及建筑物 | 41,744,687 | 尚未办完所有手续`` 实际上**全是值**，
  凑出 ``键|值|键`` 的假交替。
- **根因**：`return "value" if any(ch.isdigit()) else "key"` ——
  财务表里大量列是**文本值**（原因/说明/状态/名称/地址/担保类型）。
- **危害**：理论上可让 4 格普通数据行被误判为横表。当前语料未触发
  （P186_T134 只有 3 格，未达 `parse_kv_row` 的 4 格门槛），但属结构性风险。
- **修复**：改用结构守卫——**父表有表头 ⇒ 不是 kv_row**（ADR-020 修订）。
- **测试**：`test_table_with_header_is_never_kv_row`、
  `test_same_row_without_header_is_kv_row`（同一行，仅表头有无不同）
- **教训**：用**结构事实**判类型，不要用**内容特征**猜类型。

### 坑-23 `rowspan` 只记录不展开，第二层表头整体左移
- **症状**：`P13` 首行是 `['', '快报产量', '', '', '快报销量', '', '']`，第二行
  `['本报告期', '上年同期', …]` 从第 0 列开始摆，与上层分组错位一格。
- **根因**：`_HTMLTableExtractor` 的 docstring 明写「`colspan` 会被展开，`rowspan`
  只记录不展开」。被 `rowspan` 覆盖的格子从未填进后续行。
- **修复**：抽出 `raw_rows`（原始单元格 + rowspan/colspan），用
  `_expand_merged_cells()` 统一建网格：`colspan` 按列位置展开，`rowspan` 用
  `pending[(row, col)]` 把首格内容下发到被覆盖的每一行。
- **连带修正**：保留行的判据从「展开后是否全空」改为「**本行自有单元格是否有非空
  文本**」——占位行被进位内容填满后看起来像真实数据行，必须用自有格判断。
- **测试**：`test_rowspan_is_expanded_into_following_rows`、
  `test_rowspan_placeholder_row_without_own_cells_is_dropped`

### 坑-24 双层表头的第二层被当成数据行
- **症状**：`P29` 的 `2025年/金额`、`2024年/占营业收入比重` 等列名留在 `rows` 里；
  `P262`/`P263`/`P264` 更严重——第二层整行被当成「1 行数据」，`kind` 误判为 `kv`。
- **根因**：`header_offset = 1 if first_is_header else 0`，只吃一行表头。
- **修复**：ADR-021 的 R1/R2/R3 + 压平。`header_offset` 改为实际层数。
- **副作用（预期）**：这 3 张表的 `kind` 从 `kv` 变 `data`，原来的假 `#S01`
  段消失、数据并入 `#S01`。数值指纹逐张核对**完全一致**（只是换了段号）。
- **测试**：`test_rowspan_is_expanded_into_following_rows`（断言 2 层与压平结果）

### 坑-25 空 table 占位块被丢弃，跨页表页码区间恒为单页
- **症状**：`P94_T57` 有 165 行，`page_start == page_end == 94`，实际覆盖 P94–P103。
  引用「第 X 页」的 L0 凭证全部失真。
- **根因**：`mineru_client.content_list_to_pages` 的 `if not text.strip(): continue`
  把 MinerU 留下的空 table 块一并跳过。空块里没有内容，但它的 `page_idx` 就是
  「表续到了这一页」的唯一证据。
- **修复**：ADR-022。`page_end` 回填 + 三条护栏。
- **测试**：`test_empty_table_placeholder_extends_page_end` 等 4 项 + 缝合侧的
  `test_multi_page_anchor_block_keeps_its_page_end`。
- **连带**：`diff` 报告要认得「改号」——表号从 `#P94_T57` 变成 `#P94-P103_T57`
  时，kind / 行数 / 数值指纹全不变，不配对的话读起来像「29 张表消失了」。

### 坑-26 「算出来了」不等于「传下去了」
- **症状**：步2 明明测出 45 张多层表头，但按 `len(logical.header_rows) > 1` 统计
  **0 张**。
- **根因**：三层都已具备（`TableBlock.header_rows` 有、压平也做了、
  `_build_one()` 里甚至写了透传代码），但 ① `StitchedTable` 缺字段、
  ② `emit()` 主路径没传参，信息在中间层断掉；`_build_one()` 是**从未执行**的兜底分支，
  所以既不报错也不生效。
- **教训**：判据算对之后，必须**从最终消费端反查一次**——用下游字段统计一遍，
  而不是用上游统计充数。
- **测试**：`test_logical_table_inherits_multilayer_header_and_title`

### 坑-27 两列表被当作「可切分」，切一次就丢一行
- **症状**：`P72_T43` 的「本次现金分红情况」「其他」两行在 `page_anchored.md` 里有，
  逻辑表里没有——**静默删数据**。
- **根因**：切分判据只看「全宽合并行」（信号 A）和「仅首列非空 + 标题形态」（信号 B）。
  键值表恰恰**每一行都只有首列非空**，于是每一行都成了切分点；切完的空段又被
  `if not segment: return` 丢掉，行只剩一节 `section_path`。
- **为什么没被发现**：`section_path` 里还留着那句文字，肉眼扫过去「东西是在的」。
- **修复**：**两列表一律不切分**（`if width > 2` 才收集候选）。标签正是键值表的键，
  切掉等于删行。
- **测试**：`test_narrow_table_keeps_label_rows_instead_of_splitting`

### 坑-28 末行当切分点，整行消失
- **症状**：`P183_T130` 末行「上述金融资产包括基金投资和其他股权投资。」消失。
- **根因**：末行是切分候选，切完之后后面没有数据行，段为空 → 整行被丢弃。
- **修复**：`index >= len(rows) - 1` 时不切，并把原因写进 `cut.reason`
  （「末行，无可切分内容，保留为数据行」），`result.cuts` 仍记录以便审计。
- **测试**：`test_trailing_label_is_not_a_cut_point`

### 坑-29 表头被 MinerU 拆成表格前的若干标题块
- **症状**：`P242_T236`/`T237` 两张关联方表 `header=None`，首行数据被当成表头候选。
- **根因**：MinerU 把表头行的每个单元格输出成**独立的 `text_level=2` 文本块**，
  表格 HTML 从第一个数据行开始：
  ```
  [02] text 与本集团发生交易的合营企业和联营企业如下：
  [03] text(level=2) 公司名称
  [04] text(level=2) 关联方关系
  [05] table <tr><td>深圳壳牌比亚迪电动汽车投资有限公司</td><td>联营企业</td></tr>
  ```
- **修复**：`content_list_to_pages` 维护「紧邻表格的连续标题块」`heading_run`；
  表格没有表头时，去掉开头带编号的章节标题（`4、其他关联方`），
  若剩余格数**恰好等于列数**且每格 ≤12 字，就当作表头。
  三条约束都是结构事实，没有经验阈值。
- **误报**：全篇 scan 只命中 P242 两张，误报 0；负例（格数不符、中间夹正文）都有测试。
- **测试**：`test_heading_run_before_table_becomes_its_header` /
  `test_heading_run_with_wrong_cell_count_is_not_a_header` /
  `test_heading_run_breaks_on_intervening_text`

### 坑-30 数值归一取 10 位有效数字，「元、两位小数」口径凭空差 30
- **症状**：赛力斯现金流恒等式报 `190,501,783,200 − 161,588,039,900 =
  28,913,743,300`，表列净额却是 `28,913,743,330`，差 30。
- **根因**：`_parse_number()` 用 `f"{value:.10g}"` 归一。以「元」为单位、
  保留两位小数的报表，一个数就有 14 位有效数字（`190,501,783,194.92`），
  截到 10 位变成 `190,501,783,200`。比亚迪用「千元」整数，位数少，问题不显。
- **修复**：解析改 `f"{value:.15g}"`（double 的全精度）。
  **数值指纹另走 `_fingerprint_token()`**（仍取 10 位有效数字）——
  指纹只回答「数字动没动」，换精度不该让历史快照全部变成「数值已变」。
- **教训**：归一化精度是「判据输入」的一部分。精度不够的归一化不会报错，
  只会让所有等值判断悄悄失败。

### 坑-31 汇总块判据是统计量，换一家公司全错
- **症状**：赛力斯 19 张 `summary` 里 16 张是现金流分段（`1.持续经营净利润…`）；
  比亚迪 7 张里 2 张是「本科(人)」「30岁以下(人)」这种数据行。
- **根因**：判据是「后继行非空格 ≤4」。中文财报里「附注七」这类列大量留空，
  数据行本来就只有 3 个非空格；换成「元」为单位后表更窄，误判更多。
- **修复**：改看**分节标签的语义**——含「合计/小计/总额/总计」才算汇总块，
  另加「表宽 ≥4」挡住窄表（3 列 12 行的块按标签判会得到「半张表是汇总区」）。
  修完两份年报各只剩 1 张真汇总块。
- **教训**：统计量判据在单份 PDF 上调得很准，恰恰是最危险的信号——
  它调的是**这份文档的排版**，不是**这类文档的规律**。

### 坑-32 噪音块已打标，渲染时却照写
- **症状**：`page_anchored.md` 里每页顶着「比亚迪股份有限公司 2025年年度报告全文」，
  共 263 行；`NoiseReport` 却显示剥离了 0 行。
- **根因**：噪音判定没丢——MinerU 的 `header`/`footer` 由 `_NOISE_TYPES` 打成
  `is_noise=True`，`strip_running_noise` 只统计**自己**删的行，所以报表是 0；
  但 `render_page_anchored_markdown()` 不看 `is_noise`，把标了记的块照样写进正文。
  **「判定生效」和「产物体现」是两件事。**
- **修复**：渲染时 `if block.is_noise: continue`。
  比亚迪 10663 → 9034 行、赛力斯 14734 → 12718 行，残留 0；
  表格快照零变化（噪音块本来就不参与表格）。

### 坑-33 整行表头的第 0 格是空 `<td>`，整行被当成数据
- **症状**：`P150_T85` 折旧年限表的表头 `['', '估计使用年限', '预计净残值率', '年折旧率']`
  没被识别，`rows[0]` 成了这一行；同类的还有 `P248_T245`、`P267_T277`、
  赛力斯 `P10_T15` 等，两份年报共 **23 张**。
- **根因**：判据③要求「首行 ≥2 个非空格」。这里只有 1 个（第 0 格是空 `<td>`），
  于是落空；冒号兜底也不适用。**这个空 `<td>` 是 MinerU 的真实输出**，不是解析 bug。
- **为什么不能放宽「首行 ≥2 非空格」**：那条护栏挡的是「全宽单格表标题」（P89）。
  两个场景都表现为「非空格很少」，只能靠别的结构特征区分。
- **修复**（`markdown_blocks.py` 判据⑤）：首行第 0 格为空 + 其余格是短文本
  （≤`_MAX_HEADER_TAIL_CELL_CHARS`=20 字，排除被截断的残句）+ 后续数据行里
  **至少 2 行**第 0 列有值（证明第 0 列是真数据列，只是列名丢了）。
  第 0 格保留空串，**不编造列名**。
- **没有要求「本行无纯数值」**：赛力斯的表头就是 `['', '2024', '2025', '同比']`，
  加这条反而会漏。
- **实测**：比亚迪 12 张、赛力斯 11 张被纠正，类型分布**不变**（317 / 377），
  守恒律两份全过（14/14、11/11）。赛力斯有 3 张 `numeric_digest` 变化——
  被吞的年份数字（2024/2025）离开数值集合，正是想要的效果。
- **副作用**：`P167_T96`、`P171_T107`、`P221_T213`、`P222_T214` 顺带补出了第二层表头
  （`2025年/账面余额` 这种），说明判据⑤与 R1/R2/R3 能串起来用。

### 坑-34 复选框行带 `text_level`，被当成章节标题继承进 `section`

- **现象**：比亚迪 `P71_T42` / `P72_T43` 的 `section` 是「适用 □不适用」，
  `P107_T59` 是「适用□不适用」，`P108_T61` 是「☑ 适用 □不适用」；赛力斯
  `P69_T72` / `P109_T96` 是「√适用 □不适用」。两家共 **6 张**。
- **根因**：MinerU 给这类版面元素打了 `text_level`，而 `_is_heading()` 只认它是否存在。
- **修法**：`_is_box_line()`（含盒符且 ≤15 字）并在 `_is_heading` 分支排除；同一个
  过滤器也用在表外标题回溯里——否则会出现「`caption` 空着、`section` 是个假标题」的组合。
- **验证**：修复后两家 `section` 含盒符的均为 **0** 张。

### 坑-35 「编制单位：××公司」是报表抬头，不是表名

- **现象**：赛力斯现金流量表、所有者权益变动表上方的「编制单位：赛力斯集团股份有限公司」
  被当成表外标题收录（实测 9 处）。
- **根因**：`_UNIT_LINE_RE` 只认「单位：」「币种：」，没认「编制单位：」。
- **修法**：正则扩成 `^(单位|币种|编制单位|金额单位)\s*[:：]`，命中即跳过继续回溯。
- **教训**：单位/抬头类元数据是**开放式清单**，换一家公司就会多一种写法。凡是
  「短句 + 冒号 + 固定名词」的抬头行，优先归到元数据而不是表名。

### 坑-36 「说明文 / 长段落 / 一两个字」都会挡住表名回溯

- **现象**：`caption` 取成了正文句子而不是表名。`P105_T94`、`P106_T95` 取到
  「本集团以共同信用风险特征为依据将应收账款分为不同组别。」；`P187_T242` 取到
  「2025 年度本集团由于战略调整新设了 9家子公司…」；`P167_T193` 只取到一个「无」。
- **根因**：回溯只跳过噪音、空块、期间标签、单位行、目录行、复选框，遇到第一个
  「像文本」的块就收工。可是表格上方常常先是一句说明文，真名在它上面一层。
- **修法**（`_resolve_caption`）：① 以「。」收尾的整句**继续往前**；② 长度 < 3 的块
  （「无」「是」「否」）跳过——那是溢出格；③ 长度 > 80 的段落也**继续往前**（原先
  直接判 `missing`，P150 因此丢掉真名「14、固定资产」）；④ 回溯时用 `bbox` 上边距
  确认候选在表格**上方**。
- **教训**：「不像表名」和「不是表名」是两件事。前者要继续找，后者才停下。把
  「太长 / 太短」当成终止条件，就会在真名还压在上面时提前收工。

### 坑-37 MinerU 内容列表不是版面序

- **现象**：赛力斯 p167 的表格是页面**顶部**唯一内容块，但列表里它前面还排着一个
  「无」（`bbox_y=743`，页面底部）；p72 也有类似一处。
- **根因**：MinerU 正文按阅读序排，页眉页脚统一追加到该页末尾，个别块也会排错。
- **修法**：`_block_top()` 取 `bbox[1]`；同页回溯时 `0 <= table_top < top` 的候选跳过。
  取不到坐标（离线构造的用例）时返回 `-1`，等于不做位置校验。
- **教训**：拿「列表相邻」当「版面相邻」用，在个别页面上会静默取错。

### 坑-38 报表两期并排时，取列按「数值最多」会取到上期

- **现象**：长安半年报 `P42-P43_T37#S02` 的「投资活动」恒等式报失败，值是
  `3,043,609,246.17`——那是 **2024 年**那列；本期是 `-2,533,491,781.73`。
- **根因**：`_first_numeric_column()` 挑「数值最多的列」。两期并排时本期常有两格空白，
  上期满格，于是选中上期。**「更满」不等于「更相关」**。
- **修法**：改取**最左边**那个「多数行是金额」的列（`_looks_like_money`：带千分位/小数点
  或 ≥5 位数字，顺便排掉「附注七」列里 62、61 这类附注号）；没有明显金额列时退回旧规则。
- **另一处**：`_row_value()` 的 `column` 参数**从未生效**（一直取行内第一个数值），
  新增 `_amount_in_column()` 按列精确取值，且**单元格为空**（不是缺行）时记 `0`——
  母公司现金流量表整段留空是真实的（PDF 原文为空），真丢数据时等式仍对不上。
- **教训**：判定「取哪一列」也是判据，和「取哪一行」一样需要单测。

### 坑-60 括号是负数，不是注释（601127 2023 四项缺失）

**症状**：601127 2025 年报的 2023 列 `净利润 (2,449,687,107.34)`、`eps (1.63)`、

**测试**：`test_prompt_treats_parenthesized_number_as_negative`。

### 坑-64 `segment_facts` 有两个唯一键，DuckDB 的 `ON CONFLICT` 必须写冲突目标

**症状**：重灌时报 `Binder Error: Conflict target has to be provided for a DO UPDATE
operation when the table has multiple UNIQUE/PRIMARY KEY constraints`。

**根因**：`segment_facts` 同时有 `segment_id` 主键和
`(company, period, dimension, segment_name, metric, source_doc)` 唯一键；DuckDB 不知道该按哪个冲突处理。

**修复**：`INSERT ... ON CONFLICT (company, period, dimension, segment_name, metric, source_doc)
DO UPDATE SET value_norm = EXCLUDED.value_norm, ...`，把幂等键写全。

**教训**：表上多于一个唯一约束时，「插入或替换」不是默认行为，必须显式指名业务键。

### 坑-65 草稿页的路径带 `_draft/`，claims 却按逻辑路径记账

**症状**：编译器把带直接数字（未走 claim）的页面也转成了 active；`test_direct_number_blocks_promotion` 失败。

**根因**：`page_issues` 拿 `_draft/summaries/x.md` 去和 claims 表的键
`summaries/x.md` 比对，一条也对不上；R9 生成的问题又按页面路径过滤，于是草稿页的

**修复**：`_page_rel()` 去掉 `_draft/` 前缀，草稿页与正式页共用同一逻辑键。

**教训**：账本键和文件路径必须是同一个坐标系；草稿只是物理位置不同，不是另一套 ID。

### 坑-66 wikilink 的显示文本会被当成正文数字

**症状**：给摘要页加「延伸阅读」后，R9 报三个探针页「数字没有 claim 覆盖」，
内容却是 `返回摘要：[[summaries/002594_2025_年报|002594_2025_年报]]`。

**根因**：`_sentence_numbers` 只把 wikilink 换成显示文本，`002594_2025` 里的数字仍被正则抓到。

**教训**：正文抽取规则要先「去掉结构性标记」再抽数字，顺序反了就会误报。

### 坑-67 百分数占位符后面又补了一个 `%`

**症状**：分产品页出现 `20.49%[^c11]%`，渲染后显示两个百分号。

**根因**：claim 的显示值已含 `%`，模型按提示里的例子又在占位符后写了一个 `%`。

**修复**：提示明确「百分数占位符已含 %，不要再补」；渲染后再用
`re.sub(r"(%\[\^c\d+\])%", r"\1", body)` 兜底。

**教训**：单位到底归「值」还是归「模板」，必须在契约里写死；两边都写就会重复。

### 坑-68 草稿页与旧 active 同页并存，lint 报错了地方

**症状**：重编某文档后 lint 报「claim c16 没有脚注定义」，指向的却是旧内容；
新页面其实停在 `_draft/`。

**根因**：lint 按逻辑页名读**正式目录**，读到的旧正文配的是新 claims；真正的错误
（草稿页没用上 c16）被掩盖。

**修复**：编译流程改成「写草稿 → 写 claims → 删除同名旧 active → 校验草稿 → 转正」
（ADR-048）。

**教训**：「同一个逻辑页只能有一个物理文件」要在写入协议里保证，不能靠事后清理。

### 坑-69 模型自行计算派生数字（百分点、利润率、研发强度）

**症状**：草稿页正文出现「17 个百分点」「28.9%」「76.1%」「4.7%」，R9 报无源数字。

**根因**：目录里只有原始科目值，模型顺手做了减法和除法。

**修复**：新增命名 SQL（毛利率/净利率/研发强度/资产负债率）作为 query claim，并在
`SYSTEM_PROMPT` 里禁止任何自行计算（ADR-047）。

**教训**：只要目录里没有某派生值，模型就会自己算——「禁止」必须配套「提供」。

### 坑-70 单花括号 `{c1}` 不渲染

**症状**：草稿页正文出现 `{c1}`，数字没被替换，页面渲染成字面量。

**根因**：模型把占位符写成了单花括号；渲染器只认 `{{cN}}`。

**修复**：提示写死「必须双花括号」；R9 会把残留 `{c…}` 当无源内容报错。

**教训**：模板占位符的边界字符要在提示、渲染器、lint 三处一致。

### 坑-71 query claim 单独不能构成 l1 来源层

**症状**：分产品页被「来源不足两层（ADR-041）」挡成草稿，明明有毛利率数字。

**根因**：编译时把 `debt_ratio` 等 query claim 也加进了结构页，该页没有 facts/segments
来源，`has_enough_sources` 只认 `l1:facts#` / `l1:segments#`。

**修复**：query claim 只加在非结构页；结构页单独判断是否有 `segment_facts`。

**教训**：claim 的「来源层」与「数值种类」是两件事，账本里要分开记。

### 坑-72 「11 家」「2026Q1」这类词被当成无源数字

**症状**：概念页 R9 报「数字没有 claim 覆盖」，指向「11 家」「2026Q1」。

**根因**：R9 的数字正则匹配到公司计数和期间 token。

**修复**：`_sentence_numbers` 先剔除 `DOC_ID`、`PERIOD_TOKEN`、`STOCK_CODE`、wikilink
显示文本；概念提示禁止写「N 家」类数量词。

**教训**：数值对账要先建立「哪些 token 不是数据」的白名单，否则误报会淹没真问题。

### 坑-73 模型把占位符写进 `description`，frontmatter 不渲染

**症状**：页面 frontmatter 的 description 出现「2025 年研发费用达 {{c1}} 亿元」，index.md 直接展示占位符。

**根因**：description 由模型输出，代码只校验正文占位符；frontmatter 是纯文本，不做渲染。

**修复**：`SYSTEM_PROMPT` 规则 9 禁止 description 出现占位符/具体数字；编译时代码检测 `{{`
并用 spec 的静态描述兜底；已生成页面用一次性脚本回填。

**教训**：模型输出的每个字段都要问「这个字段会不会被渲染」。

### 坑-74 「见年报第 155 页」里的 155 被当成无源数字

**症状**：601088 研发投入页 R9 报「数字没有 claim 覆盖：相关数据见年报第 155 页 [Ref: ...#P155]」。

**根因**：R9 只剔除 `[Ref: doc#Pn]` 与期间/文档 id，正文散文里的「第 N 页」没有剔除。

**修复**：`_sentence_numbers` 先剔除 `PAGE_TEXT = 第\s*\d+\s*页`。

**教训**：白名单要覆盖「人类写法」而不只是程序写法。

### ADR-053 约束分 error / warn 两档，因为约束自己也会写错（2026-11-02）

**背景**：最初把 `acct.net_profit_le_total_profit`（归母净利润 ≤ 利润总额）写成硬约束，
真实库上 17 组违反。逐组核对后发现**约束本身错了**：所得税为负（亏损年度确认递延所得税
资产）或少数股东损益为负时，归母净利润可以大于利润总额。长安 000625 2024 即如此
（利润总额 67.5753 亿 < 归母净利 73.2136 亿，同时有 -10 亿少数股东损益）。

**决策**：

- `severity` 两档。`error` = 会计恒等式（资产=负债+权益、流动<总计、期间必填、每股单位），
  违反必为数据错误，`check` 返回非零；`warn` = 通常成立但**允许合法例外**，只提示。
- 删掉 `net_profit <= total_profit`。
- 现有 warn 四条：现金流三项闭合（差额是汇率变动对现金的影响额）、归母净资产 ≤
  所有者权益合计（少数股东权益可负）、营业成本 ≤ 营业收入（毛亏合法）、毛利率 ∈ [-1,1]。

**代价**：`check` 只按 error 给返回码，13 条 warn 需要人看。

**失效条件**：任一 warn 在某语料上**系统性**违反（不是个别合法例外），说明它其实该升级为
error；反之某条 error 若大量出现合法例外，说明判据写错，应降级或删除。两档都是可变的。

### 坑-75 给 facts 加列打断了位置参数插入与 `SELECT *` 视图

**症状**：加载本体后写事实报
`Binder Error: table facts has 20 columns but 19 values were supplied`。

**根因**：两个隐含耦合。① `insert_fact` 用 `INSERT INTO facts VALUES (19 个 ?)` 位置参数；
② `facts_dedup` 是 `SELECT *` 视图，列在创建时就绑定完了，`ALTER TABLE ADD COLUMN` 之后
视图里没有新列。

**修复**：`facts` DDL 直接带 `dict_version`；`insert_fact` 改显式列名 + `dict_version` 参数；
视图 DDL 抽成 `FACTS_DEDUP_VIEW_SQL`，在补列之后重建；补列责任交回 `FactStore`
（facts 的唯一所有者），本体层只做空库与老库的兜底。

**教训**：加列是破坏性变更。凡「位置参数插入」和「`SELECT *` 视图」都是隐式契约，要一起评估。

### 坑-76 约束验错了列，把真值报成违规

**症状**：`unit.eps_is_per_share` 报 5 条「单位应为 元/股，实际 元」。

**根因**：约束查的是 `unit_of_account`——原始表格的表头单位标注，而每股指标的表头常写成
「元」；真正该验的是归一化之后的 `norm_unit`。

**修复**：`unit_check` 解析表达式左侧列名，只允许 `unit_of_account / norm_unit / unit_family`，
配置改为 `norm_unit == '元/股'`。

**教训**：写校验前先确认「被验的那一列是不是值的权威表达」。查原始标注等于在验解析器的
口径，不是在验数据。

### 坑-77 同一个 `%` 底下藏着两种口径

**症状**：给加权 ROE 加值域约束 `-1 <= roe_weighted <= 1`，73 组里 10 组报警，值都是
15.87 / 24.05 这种「看着像百分数」的数。

**根因**：`unit_default='%'` 的概念混着两种存储口径——
- **L2 披露值**：年报原文就写「15.87」，直接入库，所以是「百分数」（15.87 = 15.87%）
- **L3 派生值**：公式 `(revenue - operating_cost) / revenue` 算出来是小数 0.1774

两套口径并存时，把 ROE（15.87）和毛利率（0.1774）放一张表里比，差 100 倍，而且**不会报错**。

**修复**：统一为百分数口径，缩放只放在 `derive.compute` 一处（`unit='%'` 的 L3 结果 ×100）——
这是全库唯一一处「由本项目定义而非抄自披露值」的数值。约束边界同步改成 -100..100 / -100..200。

**教训**：单位一致性不能靠「字段叫 unit 所以应该一致」。凡是同一字段名下存在
「抄来的」和「算出来的」两种来源，就必须显式声明缩放点，否则差异会以业务错误的形态出现。

### 坑-78 「行数最多」选出来的现金流量表是母公司的

**症状**：万科 000002 的现金流三项（经营 + 投资 + 筹资）与净增加额差 166 亿；且 `fcf` 在
2024 / 2025 两年分别是 -74.999487 / -75.002093 亿——两年几乎相同，不像真数据。

**根因**：选表器在「够不够格」里只看首行命中锚点、末行命中锚点、行数 > 2，**行数当作并列时的
胜负手**。万科母公司现金流量表 32 行、合并现金流量表 29 行（还被跨页截断），于是母公司版胜出。
更隐蔽的是 `section` 字段：合并表和母公司表的 section 都是「合并利润表」（上一次切表残留），
所以靠 section 也分不开。真正可用的判据在首行：「销售商品、提供劳务收到的现金」→ 合并；
「取得借款收到的现金」→ 母公司。

**修复**：`cash = _best_run(by_page, "cf")`——现金流量表优先取「跨页缝合后首行是销售收现」的那组，
落不进去才退回行数最多。重选后 32 份文档里只有 3 份变化，且都是变好：万科从母公司版换成合并版、
招行与广汽各补上一张真续页。

**教训**：并列判据一旦是「数量」（行数最多、文本最长、覆盖率最高），就必须先问一句
「数量多一定更权威吗」。报表尤其是：母公司表往往比合并表更长。

### 坑-79 维度成员名带「其中：」前缀，同一成员变成两个

**症状**：`upsert_segment_member` 把「新能源汽车」和「其中：新能源汽车」登记成两个 member。

**根因**：成员名归一化只去空白、括号、冒号，没去「其中」。年报里的拆分子项常写成
「其中：×××」，与主项是同一个业务对象。

**修复**：`_norm_member` 在去符号后再剥 `^其中`，原文保留在 `aliases` 里。

**教训**：同一实体的不同印法要在**归一化函数**里收敛，不要指望每个调用点自己判断。

### 坑-80 单表解析失败会拖垮整份文档

**症状**：601238_2025_年报 二次重灌后 0 条事实（旧库 67 条），而其他 28 份都正常。

**根因**：selector 改「现金流优先合并版」后，把 P109_T90 认成了现金流量表的续页。该页首行是
「其中:子公司吸收少数股东投资收到的现金」（明细行的父行），被 `split_header_blocks` 当成表头，
`column_periods` 认不出期间列 → `extract_table` 抛 `ValueError` → 一路冒到 `run()` 的
**文档级** `except` → 整份文档记 `error`，一条事实都不写。

**修复**：`extract_document` 里按**表**做 try/except，单表解析失败 `continue`，其余表照常写。

**门禁**：`tools/facts_baseline.py --update/--check` 把每份文档的事实数记成基线
（`config/facts-baseline.json`），任何文档归零或掉到基线的 80% 以下即失败，已挂进 `check.sh`。
用当时的现场复现过：删掉 601238 的 68 条事实 → `601238_2025_年报: 68 → 0（整份消失）`，退出码 1。

**教训**：批处理里的异常边界要画在「最小可丢单元」上。文档不是最小单元，表才是——
丢掉一张表只损失一个口径，丢掉一份文档会静默抹掉 67 条事实，而且不会让任何约束报错。

### 坑-81 重灌换库后 claims.fact_id 全部错指

**症状**：facts 表重建（1717 → 1762）后，`wiki.duckdb` 里 1118 条 claims 的 `fact_id`
指向了**别的事实**——两个库的 `fact_id_seq` 都从 1 开始，但插入顺序不同。

**根因**：`claims.fact_id` 存的是自增代理键。代理键只在单库单代内稳定，跨库不可迁移。

**修复**：`.tmp/remap_claims.py` 按天然键 `(company, period, metric_id, caliber, source_doc)`
回映到新库；天然键缺失时用 `(company, period, metric_id)` 唯一候选回退。结果：1115 条直接命中，
3 条值变化（正好是万科现金流被纠正的三条），未解 0。3 条所在页面已重编译。

**教训**：跨库/跨代引用不要存代理键。要么存天然键，要么存内容指纹（metric+period+值的哈希）。
这一条同样适用于将来任何「重建数据库」的操作——重灌前必须先备份 wiki 并跑一次回映。

### ADR-054 链条体检与数值校验必须分成两条命令

`check` 验的是**数值之间**是否自洽（资产=负债+权益），`audit` 验的是**每一环是否接得上**
（概念登记 / 祖先链 / 约束覆盖 / 证据字段 / 页面引用 / 派生可算）。

两者会各自报不同的缺陷：一条事实可以数值完全正确，但它的 metric 没登记概念，链条第一跳
就断了——这种断点不会让数字变错，只会让「凭什么信这个数」无从回答。

**门禁策略**：①②③④ 是**结构性断点**，任一非零即 `check.sh` 失败；⑤⑥ 是**覆盖率指标**
（页面只引用结论、派生受抽取覆盖限制），只报数不判错。

### ADR-055 维度表的种类封闭、成员开放（2026-11-02）

**问题**：现金流恒等式差的是「汇率变动对现金的影响」，权益拆分缺的是「少数股东权益」——
这类缺项会不断出现。每来一个新科目就改一次表结构，本体就会跟着膨胀。

**决策**：把「维度」和「科目」分开。
- **科目（metric）** 是有限的、由同行审计口径决定的，仍然进 `metric_dict` + 本体 L2。
- **维度（dimension）** 只做三件事：种类（分产品 / 分行业 / 分地区 / 分客户）、成员、成员层级。
  种类是**封闭词表**（会计准则披露要求决定，不会随便长），成员是**从报表行名自动抽取**的，
  新公司 / 新年度不需要任何配置文件。

**为什么不给每份年报写专用配置**：维度碰撞线在「表结构」而不是「公司」。所有公司的分部报表
长得一样（`行名 | 本期收入 | 本期成本 | 毛利率`），差别全在行名。所以抽取器按表头标记 +
section_path + 行内标记认表，按行名认成员，成员名归一化后进 `dimension_members`，多写法进
`aliases`。真正需要人工的只有「成员归并」（如「汽车」与「汽车及零部件」），那是数据治理，不是配置。

**失效条件**：如果将来出现「同一张表里两个维度交叉」（如「分行业 × 分地区」的矩阵表），
当前的 `segment_facts(一行一成员)` 表达不了，需要升级成 `fact × dim` 交叉表。

### ADR-056 率值必须带期间口径，否则半年报的 ROE 会和年报排队（2026-11-02）

**问题**：招商银行 2025 半年报写「加权平均净资产收益率 13.85%」，这是**年化**后的值；
而年报的同一字段是年度值（10.59%）。全库 64 条 ROE 事实里两者混在一起，排名、同比全错。

**决策**：`facts` 加 `period_basis`（`period` / `annualized`），由 `fact_engine/basis.py`
在全部文档写完后**反算**判定：用同 (公司, 期间, 口径) 的 `net_profit / net_assets × 100%`
作未年化参考值，再看披露值是否达到参考值的阈值倍数（半年 ≥1.5、一季 ≥2.5、三季累计 ≥1.1）。

**为什么不看文字**：厂商标注不统一，「年化」「折年」「未年化」经常不写；反算只用库里已有的
两个数，可复现、可解释，且不会因为换一家公司就失效。

**实测**：64 条 ROE 里只标出 1 条 annualized（招行 2025H1 13.85，反算 6.06，倍数 2.29）；
其余 63 条 period。保守阈值宁漏不误。

**失效条件**：净资产用期末值而非加权平均值，所以倍数不会精确等于 2/4。若将来遇到
「按期末+年化」混合披露，阈值可能误判——届时以 `period_basis` 人工覆盖为准（列可手改）。

### 8.1 一个容易误判的点

P43→P44 那张证券投资表（14 列）在 pypdf 文本层能清楚看到首尾衔接，但 **pypdf 不输出

## 10. 术语表

| 术语 | 含义 |
|---|---|
| **IR** | 中间表示。本项目的 `Page` / `Block` / `TableBlock` / `StitchedTable` |
| **物理页码** | PDF 阅读器里的页序，**1-based**。不是财报正文印刷的页码 |
| **锚点** | `[Ref: {doc_id}#P{N}]`，贯穿四层的溯源标识 |
| **doc_id** | `{股票代码}_{年度}_{报告类型}`，如 `002594_2025_年报` |
| **缝合** | 把被分页切开的同一张表拼回逻辑表 |
| **逻辑表** | `StitchedTable`，缝合产物，L1 抽取的最小单元 |
| **parent_id** | 逻辑表主键，跨页时形如 `002594_2025_年报#P43-P44_T01` |
| **签名** | 一行文本把数字替换成 `#` 后的骨架，用于识别运行页眉 |
| **噪音块** | `is_noise=True` 的块，被打标但不删除 |
| **内容块** | 非噪音块。缝合定位页首/页尾时只看内容块 |
| **续接表** | 跨页表在第 N+1 页的部分，通常**无表头** |
| **EAV** | Entity-Attribute-Value 纵表，`facts` 表的结构 |
| **重述** | 新报告对旧期间数据的会计口径修正 |
| **探针** | 编译期主动发起的财务审计提问（如「核心财务指标」） |
| **`_draft`** | 来源不足 2 个的 Wiki 页面的隔离目录，不进索引 |
